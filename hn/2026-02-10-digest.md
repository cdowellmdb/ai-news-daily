### [Thoughts on Generating C](https://wingolog.org/archives/2026/02/07/thoughts-on-generating-c)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=46957048
**Score:** unavailable | **Comments:** unavailable

#### Article Summary
This post examines the long‑running idea of compiling higher‑level languages to C as a “portable assembly.” The author explains that this approach is initially attractive because C is ubiquitous and compilers are available everywhere, so emitting C seems like a quick path to portability. But in practice, C is an awkward compilation target: the language’s semantics are underspecified in critical places, it is full of undefined behavior hazards, and different compilers can produce meaningfully different behavior and performance. When a compiler uses C as an intermediate representation, it must work around aliasing rules, integer overflow, and other UB‑adjacent traps just to preserve the source language’s semantics.

The post argues that the promise of “let C compilers do the backend work” often breaks down. To get predictable results, code generators end up avoiding large parts of C, effectively defining a constrained subset; they may also need to inspect generated assembly or rely on compiler‑specific pragmas, which undermines portability. In addition, while C output can be readable, that readability does not necessarily translate into debuggability: the generated C is still far removed from the source language’s constructs and can obscure the original intent. The author points out that if you are already bending over backwards to target a restricted subset of C and to manage compiler idiosyncrasies, you might be better off targeting a more precise IR or emitting assembly directly.

At the same time, the post acknowledges that generating C can still be viable in specific contexts. It can be a practical bootstrap step for a new language, or a way to leverage existing toolchains on unusual platforms. It can also work for certain kinds of static code generation where the mapping to C is straightforward and limited. The key is to recognize that C is not a neutral, predictable IR; it is a language with its own semantics and pitfalls. If you choose C as a target, you must treat it as a real language target rather than a magical portability layer and accept the engineering cost that comes with that choice.

The overall takeaway is cautionary: the convenience of C as a portable target is real, but the hidden complexity is substantial. The author suggests that modern alternatives like LLVM IR, WebAssembly, or domain‑specific lower‑level IRs may provide a more reliable foundation for code generation, with clearer semantics and less reliance on undefined behavior or compiler quirks. Generating C can work, but only when the constraints are well understood and intentionally embraced.

#### Comment Thread Overview
HN commenters debate whether C remains a practical compilation target in 2026. Several posters agree with the author’s critique, noting that undefined behavior and compiler differences make C a risky IR when you need semantic fidelity. They mention that real‑world projects often end up restricting themselves to a “safe subset” of C and still have to juggle compiler flags and code patterns to avoid optimizer surprises. Some add that while C may be ubiquitous, it is no longer the best portability story, since modern toolchains for LLVM IR or WebAssembly are widely available and provide clearer semantics.

Others are more sympathetic to generating C, arguing that it still offers broad compatibility and convenient integration with existing build systems. A few point to specific environments where C is the only realistic target (e.g., unusual embedded toolchains), or where the goal is simple bootstrapping rather than long‑term maintenance. The thread also surfaces a pragmatic perspective: even if C is “bad,” it can be good enough for certain constrained translations, and some teams accept the tradeoff in exchange for toolchain reach. Overall sentiment is mixed but technical: commenters appreciate the nuance and largely agree that “C as portable assembly” is far less straightforward than it appears, even if it can still be useful in narrow cases.

### [AI makes the easy part easier and the hard part harder](https://www.blundergotan.com/articles/ai-makes-the-easy-part-easier-and-the-hard-part-harder)
**Categories:** LLMs, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=46958560
**Score:** unavailable | **Comments:** unavailable

#### Article Summary
This essay argues that AI coding tools compress the easiest parts of software work while intensifying the hardest ones. The author’s thesis is that the traditional bottlenecks in software delivery were never the basic mechanics of writing code — boilerplate, straightforward CRUD, initial scaffolding — but rather the “hard parts”: architectural decisions, debugging, design tradeoffs, and integration into real systems. AI makes those easy parts nearly instantaneous, but that doesn’t reduce the cognitive load; it concentrates it. As a result, developers spend a larger share of their time on judgment, understanding, and system‑level thinking.

A key point is the difference between generation and integration. AI can generate large volumes of plausible code quickly, but the hard work is making that code correct, coherent, and maintainable within the constraints of the real system. The author describes how the surface plausibility of AI output can be dangerous: it looks right, compiles, and might even pass shallow tests, yet still embed subtle bugs or mismatched assumptions. That means a larger burden on review, architecture, and deep debugging. In effect, the easy part being automated exposes how much of the job was always about reasoning, not typing.

The piece also highlights the impact on skill development. When juniors rely heavily on AI for first drafts, they risk skipping the formative steps that teach deep understanding. The author worries about a “competence gap” where developers can prompt but cannot debug or explain what their generated code actually does. This is not framed as an anti‑AI stance; rather, it is a warning that the nature of expertise shifts. Teams must invest more in rigorous review practices and in making sure that people still learn the underlying fundamentals.

Another theme is that AI can increase the volume of work, not just its speed. If you can produce more code quickly, you also create more surface area for bugs, tests, and long‑term maintenance. The author suggests that productivity claims should be evaluated in terms of net value delivered, not raw lines of code or speed to first draft. AI’s promise is real for prototyping and boilerplate, but it does not eliminate the complexity of making software robust, safe, and fit to purpose.

The essay concludes by encouraging a deliberate posture: use AI to remove drudgery, but expect the “hard parts” to remain the core of the job. The most effective teams will be those that treat AI output as a starting point rather than a finish line, and that reinforce the human skills — architecture, design reasoning, and debugging discipline — that AI cannot replace.

#### Comment Thread Overview
The HN thread broadly agrees with the core idea but adds nuance. Several commenters note that AI makes it easy to produce more code than you can effectively review, increasing the importance of architecture and rigorous evaluation. Others point out that the “hard part harder” effect is most visible on complex, ambiguous projects where requirements are fuzzy or where correctness matters; for straightforward tasks, AI can be a near‑unambiguous win. A few commenters frame this as a shift in the locus of expertise: the job becomes about supervising, constraining, and validating AI output rather than manually drafting everything.

There is also discussion of developer skill development. Commenters worry that heavy reliance on AI for boilerplate could weaken fundamentals, making it harder to debug deep issues later. Counterpoints suggest that AI can be used as a learning tool if developers are disciplined about understanding the output. Some commenters emphasize that the best results come from pairing AI with strong testing culture and clear specifications; without that, AI output becomes a liability. Overall sentiment is thoughtful and mixed: most people find the thesis resonant, but they emphasize that outcomes depend on how teams adapt their workflows, testing, and review habits.

#### Article Summary
In this update, David Crawshaw reflects on how agent tooling and coding models have evolved over the past year and how that has changed his own programming workflow. He notes that while models have improved dramatically, the “agent harness” — the tooling and environment that wraps an LLM to make it useful — has not improved nearly as much. He argues that harness design is critical and still under‑explored, likening it to a space where significant innovation remains possible. The implication is that better tooling and integration could unlock much more practical value from models that already perform well.

Crawshaw emphasizes the pace of model improvement in practical coding outcomes. He describes a qualitative jump from models that could handle a fraction of his code to models that can now draft the majority, while still needing human review and adjustment. This progress, he argues, is a meaningful economic signal, because it shifts the balance of developer time away from writing and toward reading, reviewing, and shaping. He says that his own time split has swung dramatically toward reading and validating output, a pattern many developers are now experiencing.

He also describes a personal shift away from IDEs. While IDEs and code completion once felt inevitable, he now finds agent workflows more effective and has returned to a lighter editor setup. This is framed as a reversal of the trend that Copilot‑style tooling had set in motion. Alongside that, he makes a strong argument for using only frontier‑grade models in agent workflows. Cheaper or weaker models, he says, teach the wrong lessons because their limitations are too severe; if you want to understand what’s possible, you must use the best models available.

Another major theme is sandboxing. Crawshaw argues that built‑in agent sandboxes are inadequate — they block legitimate operations and create friction — so he recommends using fresh virtual machines as a safer and more flexible environment for agents. This connects to his broader project work on exe.dev, which he describes as a way to quickly spin up isolated environments where agents can work on small tasks or build throwaway programs. He views this as essential infrastructure for the new kind of programming that agent tools enable.

Finally, he reflects on the broader social and product implications. He is enthusiastic about the increased joy and creative output enabled by agents, but acknowledges broader concerns about labor shifts and the societal impact of powerful AI tools. He argues that software needs to be reshaped for agent use and offers a guiding principle: the best software for agents is whatever is best for programmers. In a world where every customer may have an agent writing code against your APIs, he suggests that developer‑friendly products will win.

Some agree that harness and workflow design are the key bottlenecks now, noting that many agent tools feel like “thin wrappers” around models rather than robust systems. Others push back on the claim that IDEs are waning, arguing that many developers still rely on IDE features and that the transition away from them is not universal. The idea of abandoning sandboxes in favor of fresh VMs sparks debate: commenters like the practical security boundary, but some note the overhead and complexity of constantly managing VM environments.

There is also discussion of the cost and access implications of “frontier‑only” model use. Several commenters agree that weaker models can mislead users about what’s possible, but others point out that cost and privacy constraints make local or cheaper models attractive, even if they are less capable. The thread includes both enthusiasm and skepticism about the future of agent‑driven development; many like the optimistic tone about increased productivity, while others caution that the hype can obscure real limitations.
