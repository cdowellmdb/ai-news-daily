### [Parse, Don’t Validate (2019)](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)
**Categories:** Coding Improvements  
**HN Link:** https://news.ycombinator.com/item?id=46966277  
**Score:** 409 | **Comments:** 197

#### Article Summary
This essay argues for a mindset shift in input handling: instead of “validating” raw inputs with ad‑hoc checks, you should parse inputs into precise, well‑typed representations and make invalid input unrepresentable. Validation, in this framing, is a weaker guarantee because it treats raw, loosely typed data as “good enough” if it passes a pile of predicates. Parsing, by contrast, converts input into a structured type that encodes the rules you care about. The payoff is more reliable code, better error handling, and fewer edge‑case bugs.

The article’s core example is a common pattern: take a string, run a handful of checks (non‑empty, length bounds, matches a regex), then pass it deeper into the system as a “valid” string. The author calls out the failure mode here: those checks do not change the type, so subsequent code can still misuse the value or violate assumptions. By parsing into a dedicated type (often with a “smart constructor”), you ensure that any value of that type is guaranteed to obey your constraints. This approach turns runtime checks into a one‑time conversion step, after which the type system becomes your guardrail.

The essay frames “parse” broadly: it includes turning raw text into richer domain types, splitting an input into fields, transforming external data into internal representations, and creating domain‑specific types (e.g., NonEmpty lists, bounded numeric types, constrained strings). The author emphasizes that parsing is not only about formats like JSON or CSV; it’s about encoding invariants and structure at the boundary. This clarifies the difference between “the string is non‑empty” and “this is a valid username,” which should be different types with different constructors.

A notable technical point is error reporting. Validation often results in generic boolean checks, but parsing can return structured error values that explain what failed and where. That makes both debugging and user feedback substantially better. The article suggests that good parsers preserve context, allow precise error messages, and make it easier to accumulate multiple errors where appropriate. This is not just an ergonomic improvement — it helps ensure that invalid inputs are caught early and explained accurately.

The author also discusses the interplay with functional programming practices, including algebraic data types, pattern matching, and explicit error handling (e.g., `Either`/`Result` types). These patterns make it natural to “parse” as a function that returns a structured value or a failure. But the argument is language‑agnostic: even in languages without strong static typing, you can mimic the idea with explicit constructors, value objects, or schema‑driven parsers. The key is that downstream code should operate on a representation that makes illegal states unrepresentable.

Limitations and caveats are acknowledged implicitly: parsing is not free, and it can be more work up front. There is also the practical tradeoff of creating more types and constructors, which can feel heavier for small projects. But the thesis is that this upfront cost pays dividends in correctness and clarity. Another subtle point is that “parsing” doesn’t eliminate validation — it relocates it. The validation logic still exists, but it’s embedded in parsing and becomes a conversion boundary rather than a scattered set of checks.

Why it matters: this is a concrete, practical guideline for writing safer code, especially in systems that ingest external input (user data, files, network requests, configuration). The approach reduces bugs by preventing “invalid” values from flowing through the system, and it aligns with a broader shift toward explicit domain modeling. For teams dealing with complex validation logic, adopting a “parse, don’t validate” mindset can lead to cleaner code, better error reporting, and clearer invariants. It also lays groundwork for better testing: you can focus tests on parsers and then assume the rest of the code works on valid data.

#### Comment Thread Overview
The comment thread is largely positive, with many developers agreeing that the idea is sound and resonant with their experience. Several commenters emphasized that “invalid state unrepresentable” is a powerful guiding principle and that strong types or value objects are an effective way to achieve it. Others noted the practical benefits in error reporting and debugging: when parsing happens up front, errors are localized and more explainable.

There is also a healthy dose of pragmatism. Some commenters pointed out that not all languages or teams can afford the overhead of elaborate domain types, particularly in dynamic languages or in projects with limited time. They discussed incremental adoption: start by parsing the most critical inputs or most error‑prone boundaries, rather than trying to model everything perfectly. This aligns with the article’s implicit tradeoff between up‑front effort and long‑term safety.

A few commenters brought up real‑world experiences where validation‑only approaches failed, leading to “stringly typed” values that later caused bugs or awkward checks throughout the codebase. They contrasted this with systems that used smart constructors or schema‑driven parsers and found those systems easier to maintain. The discussion is less about rejecting validation altogether and more about relocating it into a boundary‑parsing layer.

Alternative approaches were mentioned in passing, including schema validation libraries and runtime type systems, but the dominant view was that the article’s framing is broadly applicable. The thread’s most insightful contributions focused on how to apply the idea in languages with weaker type systems, and on when the additional type modeling is worth the cost.

The post emphasizes that Vulkan has accumulated many features and permutations as it evolved, and while this flexibility is good for low‑level control, it can be intimidating and error‑prone for new adopters. Although the visible content does not enumerate precise API changes, the overall direction is consistent with other Vulkan ecosystem efforts: offering clearer “happy paths” and reducing the number of mandatory choices a developer has to make for common cases.
