### [I Improved 15 LLMs at Coding in One Afternoon. Only the Harness Changed](https://aider.chat/2026/02/12/harness.html)
**Categories:** LLMs, Coding Improvements, AI Agents
**HN Link:** https://news.ycombinator.com/item?id=46988596
**Score:** 247 | **Comments:** 112

#### Article Summary
The author argues that today’s “coding benchmarks” mostly measure harness quality, not model skill. They ran a 16‑model benchmark using the Aider Polyglot React benchmark and held the code‑editing harness constant across all models. The main change was replacing Aider’s default edit tool (a patch‑style format) with a new “hashline” edit tool that includes per‑line hashes and explicit line numbers. The author reports that this reduced malformed edits and silent failures, and that simply swapping the edit tool improved results for 15 of 16 models in under an afternoon’s work. The write‑up describes three edit‑tool variants: the default “patch” format, an “edit” format similar to `search/replace` blocks, and the new “hashline” format that makes the model enumerate the affected lines, include hashes, and be explicit about replacements. The hashline format is designed to avoid a long‑standing failure mode where the model “edits” lines that no longer exist or collides on repeated line content.

The benchmark results show that weakly performing models can benefit dramatically from the more robust edit harness. The author highlights that Grok‑2 and GLM‑4.5 (and other mid‑tier models) show the largest gains; in some cases, scores roughly double and the number of failed edits drops. There is also a discussion of total token output: the hashline format tends to be shorter than patch‑style edits for small changes, which reduces output token overhead. The post notes that the best‑performing models (Claude 3.5 and GPT‑4‑class models) already had strong baseline performance, but still improved modestly when the harness was more deterministic and constrained. The author links to the benchmark code and results tables, and points out that the relative ranking of models changes when the harness changes, implying that “model A beats model B” claims are contingent on harness details.

A large part of the essay is a call to focus more on harness engineering and evaluation transparency. The author argues that vendors quietly ship specialized editing tools, speculative patch formats, or model‑specific prompts, which makes it hard to compare results across tools. They cite examples: Cursor’s use of a separate “planner + executor” setup, JetBrains’s “Diff‑XY” style edits, and Anthropic’s “XML‑like” tool outputs. The conclusion is that benchmarking should explicitly report the harness, edit tool, and formatting constraints, and that improvements in “coding performance” can often be achieved by better orchestration and tool design rather than new model weights. The post also notes a recent support incident where the author’s access was restricted, highlighting fragility for independent benchmarking and the need for open harnesses.

#### Comment Thread Overview
The comment thread is largely appreciative of the “harness first” framing. Many readers say the post matches their experience: model quality is often less important than the structured edit protocol and the reliability of the tool chain around the model. A common theme is that patch‑style diffs are brittle for LLMs because they require exact context matches and often fail silently; several commenters say they switched to `search/replace`‑style blocks, tree‑sitter‑aware edits, or intermediate AST transforms to reduce error rates. A few readers highlight that the hashline approach feels similar to checksumming in file transfer and that explicit line anchoring is a simple but effective constraint.

There is also skepticism about the broader implications: some commenters argue that tighter harnesses can overfit to benchmarks and might reduce flexibility on real tasks, while others counter that reliability is the key bottleneck for production use. Several people mention Aider, Claude Code, and GitHub Copilot workflows; the consensus is that “harness engineering” is the underrated part of developer tooling. A smaller side conversation touches on how “AI‑written” style markers (like em‑dash usage) aren’t reliable, and that small prompt or tooling changes can swing results dramatically. Overall, sentiment is positive and focused on the value of transparency and reproducibility in LLM coding evaluations.

### [Text classification with Python 3.14's ZSTD module](https://www.inferencezone.com/articles/2026-02-11-text-classification-zstd-py314)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=46942864
**Score:** 228 | **Comments:** 51

#### Article Summary
This article describes a surprisingly effective baseline for text classification using the compression module added in Python 3.14: `compression.zstd`. The idea is rooted in the “compression as similarity” hypothesis, where a compressor’s ability to reduce the size of a text reflects how well the text fits a learned model of that class. The author implements a classifier that trains a Zstd dictionary per class, then measures the compressed size of a new document under each class dictionary. The class that yields the smallest compressed size is chosen as the prediction.

The post outlines practical implementation details. The author uses `ZstdDict` to build dictionaries from concatenated class examples, sets compression levels and window sizes, and notes that the compressor state must be rebuilt between documents to avoid contaminating results with prior context. The classifier runs in two phases: dictionary construction and scoring. For scoring, each document is compressed under each class dictionary, and the compressed length is used as a proxy for similarity. The article emphasizes that because Zstd is fast and implemented in C, this approach can be extremely lightweight compared to typical ML pipelines.

In a four‑class 20 Newsgroups experiment, the approach reaches roughly 91% accuracy with under two seconds of runtime, according to the author’s benchmark, and no explicit feature extraction. The article contrasts this with a classic LZW‑based approach from a 2023 paper that reportedly achieved around 89% but required far more time (tens of minutes). The author also compares against a TF‑IDF + logistic regression baseline, noting that while TF‑IDF may achieve higher accuracy, the Zstd method’s simplicity and speed are attractive for quick classification or resource‑limited environments. The piece suggests practical applications like quick topic routing, spam filtering, and lightweight document triage.

Caveats include sensitivity to corpus size, class imbalance, and the size of the dictionary. The author suggests experimenting with dictionary size and compression levels, and notes that the method is best treated as a fast baseline rather than a replacement for more sophisticated models. It also assumes that the documents are large enough for compression to capture meaningful redundancy, which may not hold for very short texts. Overall, the article presents Zstd‑based classification as a pragmatic, easy‑to‑implement approach for certain text classification problems in Python 3.14.

#### Comment Thread Overview
The HN comments are inquisitive but cautious. Several commenters point out that “compression‑based classification” is an old idea and link to earlier academic work, arguing that the novelty here is really the availability of Zstd in the Python standard library. There is debate about whether the reported accuracy is comparable to modern baselines, and some readers suggest that for many tasks a simple bag‑of‑words model or fastText classifier would outperform it without much extra complexity. A few commenters mention concerns about overfitting to the training corpus, especially if the dictionary is built from concatenated class samples that might include repeated boilerplate.

The author (or readers running experiments) responds by emphasizing the low setup cost and fast runtime, positioning it as a convenient baseline rather than a state‑of‑the‑art technique. There’s also discussion about the sensitivity to document length: very short texts may compress poorly and yield noisy similarity signals. Overall sentiment is positive toward the educational value and practicality, but the thread treats it as a “fun and useful trick” rather than a replacement for standard ML pipelines.

The release notes describe 700 commits and 49 contributors, and call out new support for modules like `Logger`, `Regex`, `URI`, `Keyword`, `String`, `StringIO`, `String.Chars`, and `StringDB`. The post frames this as unlocking a sizable subset of Elixir’s standard library for use in the browser.

The release also includes a long list of enhancements and bug fixes. Key enhancements include faster compilation via an optimization in `Agent.cast`, better handling of standard input on Windows, a new option for `float_to_binary`, and improvements to function reference equality. There are changes to improve client‑side ERTS initialization and more robust ETS (Erlang Term Storage) infrastructure. The post also calls out improved project templates and a new or improved config structure for HTML and asset pipelines. On the tooling side, the compiler now handles raw HTML blocks more directly, and the `mix setup` process is more robust across platforms, including a fallback to system Biome on NixOS.

The post explicitly notes that some modules remain out of scope for this phase, particularly those that rely on process constructs or more complex BEAM runtime behavior. The team positions these as “Phase 2” work. That caveat frames the current release as a large but incomplete step toward full Elixir parity in the browser.
