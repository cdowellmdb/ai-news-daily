### [A DuckDB-based metabase alternative](https://github.com/taleshape-com/shaper)
**Categories:** Databases
**HN Link:** https://news.ycombinator.com/item?id=47057879
**Score:** 113 | **Comments:** 27

#### Article Summary
Shaper is an open‑source, SQL‑driven dashboard system built on DuckDB that aims to make analytics dashboards feel like code. The core idea is that you write SQL statements and annotate the outputs with simple type hints (labels, axes, categories, chart types) to produce charts and dashboard sections. The docs present a canonical example where a SELECT statement defines a chart title and a second SELECT defines a stacked bar chart by choosing column annotations such as `XAXIS`, `CATEGORY`, and `BARCHART_STACKED`. This approach is meant to keep the authoring model familiar: if you know SQL, you can build the UI without learning a separate DSL or dragging blocks around a WYSIWYG editor.

Feature‑wise, Shaper focuses on dynamic dashboards that are still plain‑SQL at their core. It supports dynamic filters, chart annotations derived from the data, and conditional sections to show or hide parts of a dashboard based on query results. Because it is powered by DuckDB, it can query multiple data sources through DuckDB extensions, pre‑compute intermediate state as temporary tables, and generally lean on DuckDB’s ability to act as a unified analytics engine. The docs explicitly highlight that any DuckDB extension is available, which opens up queries over storage like S3 or over sources like Postgres and Google Sheets without changing the dashboard’s authoring model. This makes Shaper feel like a thin but opinionated layer on top of a high‑performance embedded database.

Shaper is also positioned as an embedded analytics tool. Dashboards can be embedded into applications without iframes, and the docs mention JavaScript and React SDKs to integrate within web apps. Access control can be enforced with per‑user JWTs, and dashboards can be shared externally via password‑protected links. The system emphasizes giving users access to their own data: it supports generating CSV and Excel downloads, and it can export dashboards as PDFs. These export features are called out as first‑class, suggesting that Shaper expects dashboards to be used both interactively and as artifacts that can be emailed or attached to reports.

Operationally, Shaper is designed to be simple to run. The README offers a quickstart that runs everything in a single Docker container, and the docs repeat the “simple operations” positioning: run one container, manage data via SQL, and keep infrastructure ownership. The project is open‑source under MPL‑2.0, explicitly advertising “no lock‑in” and control over data and infrastructure. For teams that want help, managed hosting and support plans are offered, but the documentation keeps the default deployment story straightforward and self‑hostable.

The documentation also frames Shaper as “more than a dashboard builder.” It positions the tool as a starting point for data projects that can grow in sophistication without forcing an immediate migration. It can store data directly in DuckDB, ingest data in real time via HTTP or NATS with automatic schema inference, and query remote data in place via DuckDB extensions. For transformation workflows, it supports scheduled tasks written in SQL, and it explicitly notes that those SQL workflows can later be moved to tools like dbt or SQLMesh as pipelines become more complex. This positions Shaper as a pragmatic on‑ramp for teams that want quick dashboards today but might need more formal pipeline management tomorrow.

The main trade‑offs are implicit in the design. The approach assumes SQL fluency and is optimized for teams that value “dashboards as code” over drag‑and‑drop self‑service. Its reliance on DuckDB extensions means coverage depends on DuckDB’s ecosystem and the data sources available there. And while Shaper handles dashboards, exports, and embedding, the docs encourage moving transformations to other tools as complexity grows, which suggests it is intended to complement, not replace, a full data platform. For teams that want a minimal, fast, SQL‑native analytics layer with embedded sharing and export, Shaper’s design is intentionally narrow and focused.

### [BarraCUDA Open-source CUDA compiler targeting AMD GPUs](https://github.com/Zaneham/BarraCUDA)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47052941
**Score:** 417 | **Comments:** 174

#### Article Summary
BarraCUDA is an open‑source CUDA compiler that targets AMD GPUs, written in roughly 15,000 lines of C99 with no LLVM dependency. The README’s headline claim is direct: it compiles `.cu` CUDA source files straight to GFX11 machine code and emits ELF `.hsaco` binaries that can run on AMD RDNA 3 hardware. This is positioned as a “just do it yourself” answer to NVIDIA’s CUDA lock‑in. The project avoids translation layers like HIP and instead implements the full compiler pipeline in‑house: a lexer, parser, intermediate representation, semantic analysis, instruction selection, register allocation, and binary encoding, all ending in an AMDGPU‑compatible output format.

The documentation spells out the compilation pipeline and confirms that every single instruction encoding has been validated against `llvm-objdump`. LLVM is explicitly not used for compilation, but is used as a validation tool to ensure that the emitted machine code decodes correctly. The build story is intentionally minimalist: a C99 compiler and `make` are the only requirements, with no external dependencies. Usage is straightforward: a single command builds a GPU binary, with optional flags to dump the IR, AST, or semantic analysis output for debugging or inspection.

Feature coverage is surprisingly broad for a small‑codebase compiler. The README lists support for CUDA function qualifiers (`__global__`, `__device__`, `__host__`), built‑ins like `threadIdx` and `blockIdx`, C control flow constructs, templates, and operator overloading. On the CUDA side, it supports shared memory, `__syncthreads`, a full suite of atomic operations, warp intrinsics such as shuffle and ballot operations, vector types, half precision, `__launch_bounds__`, and basic cooperative groups. On the compiler‑front‑end side, it implements a full C preprocessor with macros, includes, and conditional compilation, as well as error recovery and source‑location tracking in IR dumps. The README also provides a detailed breakdown of the compiler’s files and line counts, highlighting how much of the logic is hand‑written.

The GFX11 encoding notes section gives a sense of the project’s depth. It lists specific ISA quirks—bitfield layouts, opcode prefixes, wave size defaults, and contradictory documentation—underscoring that this is a low‑level effort rather than a high‑level wrapper. It also reinforces that the current scope is GFX11, with “more architectures planned” but not yet delivered. No releases are published, suggesting the project is still early and likely aimed at enthusiasts or researchers willing to tolerate sharp edges.

In practice, BarraCUDA’s value proposition is twofold. First, it demonstrates that a standalone, non‑LLVM compiler can emit working AMD GPU binaries from CUDA C, which is a technical achievement and a proof‑of‑concept for alternative CUDA toolchains. Second, it offers a path toward broader CUDA portability on non‑NVIDIA hardware if the project matures. The approach is pragmatic and minimalistic: build it in C, avoid heavy dependencies, and focus on correctness of emitted machine code.

Limitations are mostly implicit. The compiler currently targets AMD RDNA 3 and GFX11 only, which restricts its hardware reach. There is no mention of full CUDA ecosystem parity (libraries, debug tooling, profiling), and the toolchain is self‑contained rather than integrated into typical CUDA workflows. Still, as a research‑grade compiler and a statement against vendor lock‑in, BarraCUDA is a compelling artifact—and a reminder that low‑level compiler work remains accessible to a determined developer.

### [Using go fix to modernize Go code](https://go.dev/blog/gofix)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47049479
**Score:** 403 | **Comments:** 78

#### Article Summary
The Go team’s 1.26 release includes a complete rewrite of the `go fix` subcommand, and this post explains both how to use it and the infrastructure behind it. `go fix` runs a suite of analyzers that identify and apply safe, automated modernization edits across a codebase. The command takes the same package patterns as other Go tools (`go fix ./...`) and updates source files in place while ignoring generated files, under the reasoning that generator logic should be fixed at the source. The authors recommend running `go fix` after upgrading your Go toolchain, and doing so from a clean git state so reviewers can isolate the generated changes. There’s also a `-diff` flag to preview changes without modifying files.

A key part of the new system is the catalog of fixers and the ability to control them. The tool can list registered analyzers via `go tool fix help`, and each analyzer has specific documentation. Examples include `any` (replace `interface{}` with `any`), `buildtag` (check build constraint syntax), `forvar` (remove redundant loop‑variable shadowing after Go 1.22’s range semantics change), `mapsloop` (replace manual map loops with `maps` package functions), `minmax` (replace common if/else patterns with `min`/`max`), and `stringscut` (replace `Index` and slicing with `strings.Cut`). By default, all analyzers run, but flags let you enable or disable individual ones to keep reviewable diffs small. The tool also only analyzes one build configuration at a time, so projects with extensive build tags or platform‑specific files should run it multiple times with different `GOOS`/`GOARCH` to maximize coverage.

The post frames these “modernizers” as a response to the rapid evolution of Go’s language and standard library since generics. As new idioms appear, many older code patterns become needlessly verbose or error‑prone. Modernizers help keep code simpler and more idiomatic, and they also serve an educational purpose by reinforcing new patterns. The Go team expects to ship more modernizers with each release, and they now consider a modernizer alongside major language or stdlib changes as part of the proposal process.

A detailed example focuses on Go 1.26’s new `new(expr)` feature, which allows `new` to take any value rather than only a type, eliminating a long‑standing boilerplate pattern of helper functions like `newInt`. The `newexpr` fixer can rewrite these helpers to use `new(expr)` and update calls across packages when the minimum Go version is declared in `go.mod` or in build tags. This shows how `go fix` can be forward‑looking while still being version‑safe.

The post also introduces “synergistic” fixes: applying one transformation can unlock another. For example, simplifying `if`‑based clamping into `min`/`max` creates subsequent opportunities to further condense code. The tool aims to chain these safely without requiring manual intervention. It also highlights a broader theme of “self‑service” analysis: organizations and module maintainers can encode their own guidelines and best practices as analyzers, creating a pathway for domain‑specific modernization rather than relying solely on upstream language changes.

Overall, `go fix` is positioned as both a modernization engine and a lever to keep the Go ecosystem’s public corpus up‑to‑date—particularly important in an era where LLMs learn from open‑source code. The most important caveats are operational: run the tool in a clean state, apply fixers in manageable batches for large repos, and remember that results depend on build tags and target platforms. Done well, `go fix` can significantly reduce maintenance churn and keep Go code idiomatic as the language evolves.

### [Async/Await on the GPU](https://www.vectorware.com/blog/async-await-on-gpu/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47049628
**Score:** 220 | **Comments:** 54

#### Article Summary
VectorWare’s post announces a milestone: running Rust’s `async`/`await` and `Future` trait on the GPU. The company positions itself as a “GPU‑native software company,” and argues that asynchronous, structured concurrency is a better way to express complex GPU programs than today’s manual approaches. The article begins by describing traditional GPU programming as primarily data‑parallel: a single kernel operating in lock‑step across many data elements. For more complex workloads, developers increasingly use warp specialization, where different warps do different parts of a pipeline concurrently (e.g., one warp loading data while another computes). This offers more expressiveness but forces developers into manual scheduling, synchronization, and error‑prone coordination.

VectorWare surveys higher‑level approaches such as JAX, Triton, and NVIDIA’s CUDA Tile. These systems model GPU programs as graphs or blocks, use specialized DSLs, and lower through compiler pipelines (often MLIR). They provide structure and optimization, but they also require adopting new ecosystems and don’t compose cleanly with traditional CPU libraries or GPU kernels. The post argues for an alternative abstraction that keeps developers in a mainstream language while capturing structured concurrency: Rust’s `Future` trait. Futures are minimal, composable state machines whose execution model is separated from their definition, allowing them to run in diverse environments. The authors argue that this aligns naturally with GPU hardware and warp‑level task scheduling.

The technical core is a demonstration that Rust futures can be compiled to GPU code and executed. The post presents a GPU kernel that calls simple async functions, conditionals, multi‑step workflows, and combinators, all driven by a `block_on` executor on the device. This proves that the same `async`/`await` syntax used on the CPU can run unchanged on the GPU. The work required fixing compiler backend issues and addressing quirks in NVIDIA’s `ptxas` toolchain, which the team reported and worked around.

After the initial “block_on” proof, the team moved to a more capable executor: the Embassy executor, originally designed for embedded, `#![no_std]` environments. GPUs lack a standard OS runtime, so Embassy is a natural fit. The post shows a no‑std example with multiple async tasks running concurrently on the GPU, each yielding periodically to allow interleaving. The key claim is that existing Rust async libraries can be reused with minimal changes on the GPU, which is a major advantage over GPU‑specific DSLs.

The authors emphasize that the main goal is capability rather than raw performance. They acknowledge that `async`/`await` introduces runtime scheduling, and that the initial implementation uses inefficient polling. However, they argue that futures compile down to state machines, making the abstraction “zero‑cost” in principle, and that the real benefit is the ability to write more complex, task‑oriented GPU programs without inventing a new language. They also note parallel work in other ecosystems (such as C++’s `stdexec` efforts) but stress that Rust already has a mature async ecosystem to draw from.

The broader implication is a potential shift in GPU programming models. If structured concurrency can run directly on the GPU, developers could build workflows that mix data‑parallel and task‑parallel work more naturally, reuse existing Rust abstractions, and reduce the mental overhead of manual synchronization. The post frames this as a long‑term bet: the technology is early, but it shows that GPU programming can evolve beyond bespoke kernels toward general‑purpose concurrency constructs embedded in a mainstream language.

The HN discussion is technical and curious, with commenters probing how the model maps onto GPU realities. There’s interest in whether lane width should be a compile‑time constant and how to expose that safely in APIs. There’s also practitioner‑level curiosity from people working on GPU data stacks and ML pipelines. They point out the complexity of CPU/GPU orchestration in real systems and ask how async could help with data movement, inference serving, or heterogeneous workloads. The tone is largely positive—“cool experiment,” “love this”—but skeptical in the right places, especially around scheduling, runtime models, and how much of Rust’s async ecosystem can be made to work in a GPU environment. Overall, the thread treats the post as an ambitious and promising direction, with the main open questions centered on performance, portability, and tooling maturity.

### [HackMyClaw](https://hackmyclaw.com/)
**Categories:** AI Agents, LLMs
**HN Link:** https://news.ycombinator.com/item?id=47049573
**Score:** 348 | **Comments:** 178

#### Article Summary
HackMyClaw is a public prompt‑injection challenge centered on “Fiu,” an OpenClaw email assistant that reads inbound messages and has access to a secret file (`secrets.env`) it is instructed not to reveal. The site presents a simple premise: send Fiu a prompt injection via email; if the model leaks the secret in its response, you win a $100 bounty. The challenge is framed as an educational security exercise inspired by real prompt‑injection research, with explicit authorization and a public attack log. The instructions are intentionally lightweight: no signup, no setup, just email the agent. The system checks email every hour, and while Fiu can technically send email, it is only constrained by a prompt instruction not to reply without human approval—highlighting the difference between policy and hard technical controls.

The site lists example attack vectors, including role confusion, instruction overrides, context manipulation, output format exploits, encoding tricks, and jailbreak‑style persona hijacking. It emphasizes that Fiu’s protection is intentionally minimal—“10–20 lines in the prompt”—to test baseline model resistance rather than elaborate defensive prompt engineering. The rules explicitly restrict attacks to the email channel (no VPS hacking, no external exploitation), ban abuse like DDoS, and enforce rate limits of 10 emails per hour. If an attack works, the winner submits the leaked `secrets.env` contents to claim the prize.

An update dated February 18, 2026 provides important context: the organizer reports that testing conditions may have biased results because more than 2,000 emails arrived and Fiu realized he was part of a test, partly due to volume and metadata leaks. The plan is to re‑run each email in sequence on a fresh session without memory of previous attempts to see if results change. This underscores a key challenge in prompt‑injection evaluation: bulk processing and contamination can change the model’s behavior, and “attack success” can be sensitive to batching, context effects, and measurement setup.

The FAQ clarifies multiple operational details. Fiu uses Anthropic Claude Opus 4.6, reinforcing the notion that the challenge targets a state‑of‑the‑art model. The system does not reply to every email due to cost; instead, attempts appear in the public log. If an injection succeeds, the model is expected to leak the secret in its reply. The site also explains that email content may be shared later for educational examples, and that email addresses will not be disclosed. The organizer invites donations to increase the prize and cover token costs.

From a security perspective, HackMyClaw functions as a live, real‑world testbed for indirect prompt injection via email. It demonstrates the gap between “instructional” safety (a prompt telling the model not to leak secrets) and robust guardrails, and it highlights how model choice, prompt design, and operational constraints interact. The explicit allowance of creative social engineering within the email body means the test is not a toy—it reflects the kinds of manipulations real‑world agents face. The current scope is narrow (one agent, one secret, one channel), but the challenge is designed to surface practical lessons about model behavior under adversarial input.

The main limitations are inherent to the experiment: single‑vector attacks, a single target file, and a baseline prompt defense. The cost‑driven decision not to respond to all emails makes verification dependent on the organizer’s process, and the February update admits that the initial evaluation may be skewed. Still, the site is transparent about its constraints, and it provides a concrete, public experiment for tracking how prompt‑injection techniques fare against a modern model in a constrained but realistic workflow.
