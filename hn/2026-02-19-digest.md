### [Anthropic officially bans using subscription auth for third party use](https://code.claude.com/docs/en/legal-and-compliance)
**Categories:** LLMs, AI Agents
**HN Link:** https://news.ycombinator.com/item?id=47069299
**Score:** 541 | **Comments:** 653

#### Article Summary
Anthropic’s Claude Code documentation adds a clear, enforceable line between consumer subscription authentication and developer/API use. The “Legal and compliance” page spells out that Free/Pro/Max accounts authenticate via OAuth tokens intended only for Claude Code and Claude.ai, and that those OAuth tokens are not allowed to be reused in any other product, tool, or service — explicitly including the Agent SDK. The page makes the expectation concrete for third‑party developers: if you are building a product or service that interacts with Claude’s capabilities, you must authenticate with API keys through Claude Console or a supported cloud provider (Bedrock or Vertex). Anthropic says it does not permit third‑party developers to offer Claude.ai login or to route requests through Free/Pro/Max plan credentials on behalf of users. It also states that it reserves the right to enforce these restrictions without prior notice.

This doc sits alongside general licensing and compliance notes. It clarifies that Claude Code usage for enterprise/API customers is governed by their commercial agreements; and for consumer users by the Consumer Terms of Service. There’s a short section explaining that if a customer has a BAA and Zero Data Retention enabled, the BAA can extend to Claude Code traffic, but that applies to API traffic routed through Claude Code, not consumer OAuth. The “Usage policy” section further underlines that the advertised usage limits for Pro/Max are for ordinary, individual usage of Claude Code and the Agent SDK — with the new authentication boundary clarifying that “Agent SDK” is still expected to be used with API keys, not consumer OAuth.

The practical effect is that “subscription auth” (Claude.ai or Claude Code OAuth) can no longer be used as a cheap proxy for API access, even if a user is willing to authenticate. If you are building a third‑party tool, wrapper, or agent harness, you need to switch to API keys. The doc also explicitly disallows third‑party apps from offering Claude.ai login, which affects any product whose UX relied on the consumer login flow. In other words, the document is a policy and enforcement line: it formalizes which authentication methods map to which usage contexts, makes it explicit that routing consumer credentials through third‑party products is out of bounds, and signals that Anthropic may take active measures to stop it.

Several commenters argue that the switching cost is not data migration but muscle memory and workflow habits, which makes any perceived lock‑in feel especially heavy‑handed. Others counter that owning the full stack (model + harness) is strategically valuable and can deliver better integrated outcomes.

Economics are a second major thread: people note that API usage is far more expensive than consumer subscriptions, and that the restriction effectively removes subsidized “all‑you‑can‑eat” usage from third‑party tools. Some see this as a predictable move from a company trying to control costs; others call it a bait‑and‑switch and compare it to infrastructure vendors that tighten terms after adoption. There are repeated references to alternative harnesses (e.g., pi.dev and other lightweight CLI agents) that users claim already outperform Claude Code for their workflows, and to competitors advertising compatibility with Claude Code’s harness. A few commenters argue that the policy just enforces what was already in the terms, and that developers should simply use API keys; the pushback is that the price delta is the whole issue. Overall sentiment skews negative, with a mix of practical complaints (price, tooling, flexibility) and strategic critiques (ecosystem capture, reduced innovation).

### [How to choose between Hindley-Milner and bidirectional typing](https://thunderseethe.dev/posts/how-to-choose-between-hm-and-bidir/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47025885
**Score:** 120 | **Comments:** 38

#### Article Summary
This post reframes a common language‑design question — “Should I use Hindley‑Milner (HM) or bidirectional typing?” — as the wrong starting point. The author argues the real decision is whether the language needs generics, because generics imply type variables and unification. If you need generics, you need unification; once you have unification, you can implement HM‑style inference and you can also implement bidirectional typing, which the post treats as a superset. The piece sketches how HM is often presented: an `infer` function that walks the AST, assigns type variables, and solves them via unification. To make the system bidirectional, you add a `check` function that can verify an expression against an expected type. The simplest form of `check` just calls `infer` and compares or unifies the result, which already qualifies as bidirectional. From there, you can make `check` smarter for cases where the expected type is known (for example, checking a function against a function type and then checking its body against the return type), without giving up inference elsewhere.

A key point is that “bidirectional” doesn’t mean “no unification.” There are examples of bidirectional systems that avoid unification entirely by relying on annotations, but the author says this has led to a mistaken perception that bidirectional typing is only about annotated checking. In practice, bidirectional typing can incorporate unification and thus support the same feature set as HM while also accommodating features that pure HM struggles with (e.g., subtyping and more advanced type features). That is why many real‑world languages end up bidirectional even if they start HM‑ish.

The post then circles back to the “generics or not” question and lays out a decision path. If you are building a general‑purpose language, generics are effectively mandatory; the ecosystem has converged on that, from Rust and Haskell to Go. In that case, unification (and therefore HM‑style inference) becomes worthwhile despite its implementation complexity, and you might as well add the small amount of extra machinery that makes the system bidirectional. But if you are designing a learning project, a niche DSL, or a language where you can accept explicit annotations, you can avoid the complexity of full unification. Bidirectional systems without unification can still be a good fit when types are mainly there to support code generation or domain modeling rather than a full‑featured, general‑purpose type system. The author warns that successful DSLs often grow into general‑purpose languages, so skimping on generics can become a long‑term limitation. The closing advice is to decide on generics first, then choose the type‑checking strategy; with generics, bidirectional typing is a pragmatic superset that gives you flexibility.

#### Comment Thread Overview
The comment thread is a mix of practical language‑design skepticism and type‑theory enthusiasm. Several commenters argue that complex inference can hurt readability and error messages, and that requiring explicit type annotations (at least on function parameters and return types) can make programs clearer and tooling simpler. Others push back that HM is actually one of the simplest inference systems to implement and teach, with a large body of references and libraries, and that ML‑style inference is a lightweight experience for users. There’s also discussion of gradual typing as a pragmatic middle ground for languages that aim to feel dynamic while offering optional static checks.

A recurring technical point is that once you want generics and compile‑time type checking, you end up needing unification anyway, which weakens the argument for avoiding inference machinery entirely. Commenters highlight that bidirectional typing becomes necessary when you add features like subtyping, impredicative polymorphism, or advanced type applications — and that real‑world languages such as Haskell have moved toward bidirectional mechanisms for these reasons. Another thread emphasizes that while inference rules may be simple, emergent behavior can still be confusing, producing complex derivations and unintuitive error messages. Some commenters point to compositional type systems and other alternatives to improve explainability. Overall, the sentiment reflects a practical trade‑off: inference is powerful and ergonomic, but many language designers still prefer explicitness to reduce complexity and improve error quality.

### [Step 3.5 Flash – Open-source foundation model, supports deep reasoning at speed](https://static.stepfun.com/blog/step-3.5-flash/)
**Categories:** LLMs
**HN Link:** https://news.ycombinator.com/item?id=47069179
**Score:** 164 | **Comments:** 69

#### Article Summary
StepFun’s “Step 3.5 Flash” release positions itself as a high‑performance, open‑source foundation model optimized for agentic reasoning and efficient inference. The model is a sparse Mixture‑of‑Experts (MoE) architecture with 196B total parameters but only 11B active per token, which the post describes as “intelligence density.” That sparse design is used to claim frontier‑level reasoning with lower compute cost than dense models of similar capability. The blog emphasizes speed and interactivity: a 3‑way Multi‑Token Prediction (MTP‑3) setup is used to push throughput into the 100–300 tokens/sec range in typical usage, with peaks around 350 tokens/sec for single‑stream coding tasks.

Long‑context efficiency is another core claim. Step 3.5 Flash supports a 256K context window using a 3:1 Sliding Window Attention (SWA) strategy, interleaving three SWA layers for every full‑attention layer. The stated goal is to maintain accuracy on long‑range context while reducing the attention cost that typically makes very long contexts expensive. The post ties these architecture choices to an “agentic” focus: the model is described as built for longer‑horizon tasks and tool use, backed by a scalable RL training framework intended to continuously improve behavior.

The blog highlights benchmark results across multiple domains. It lists average scores across a suite of eight benchmarks and includes comparisons against GLM‑4.7, DeepSeek V3.2, Kimi K2.5, Gemini 3.0 Pro, Claude Opus 4.5, and GPT‑5.2 xhigh. For coding and tool‑use‑like tasks, the post specifically calls out 74.4% on SWE‑bench Verified and 51.0% on Terminal‑Bench 2.0, framing those as evidence of long‑horizon task ability. The post also includes reasoning benchmarks such as AIME 2025 and IMOAnswerBench, showing Step 3.5 Flash as competitive among top proprietary and open models.

Distribution is presented as open and accessible. The model is linked on GitHub and HuggingFace, with a published technical report and ModelScope listings, and the post emphasizes “accessible local deployment” on high‑end consumer hardware (examples include Mac Studio M4 Max and NVIDIA DGX Spark). The overall framing is: a large, open model that competes with proprietary systems on reasoning and coding, while prioritizing throughput, long context, and efficient local inference.

#### Comment Thread Overview
The comment thread is generally positive about an open, high‑throughput model, but it mixes excitement with skepticism about benchmark interpretation. Several commenters report local testing with 4‑bit quantizations, noting strong performance for agentic coding and unusually high token throughput on consumer hardware. One popular thread highlights compatibility with CLI harnesses and compares it favorably to other large local models; others mention it works well in certain agent workflows (e.g., pi.dev) but that some harnesses or tools (like patch‑edit utilities) can confuse the model. There are also concerns about very long reasoning chains and occasional loop behavior, with users hoping for fixes in future releases.

Benchmarks are a focal point of debate. Some commenters push back on the claim that a 51% Terminal‑Bench score proves “unwavering stability,” arguing that benchmark scales and definitions matter. Others respond that you need to compare relative positions on leaderboards, and that “agentic” performance is influenced heavily by the harness rather than the model itself — with examples where different agents achieve notably different scores on the same model. A second thread discusses efficiency and energy cost: commenters appreciate MoE’s token‑per‑joule improvements and criticize recent model releases that boost benchmark scores by inflating token usage. Overall sentiment is that Step 3.5 Flash is promising and possibly underrated, but still requires careful evaluation in real workflows.

### [Electrobun v1: Build fast, tiny, and cross-platform desktop apps with TypeScript](https://blackboard.sh/blog/electrobun-v1/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47069650
**Score:** 138 | **Comments:** 49

#### Article Summary
Electrobun v1 is presented as a two‑year effort to build a desktop app framework that feels more like “shipping the web” than wrestling with native packaging. The author describes coming from a desktop era (VB6, then Adobe AIR) and feeling that modern desktop development had regressed. An initial Electron version of their app (co(lab)) ran into painful DX around code signing, notarization, distribution, and updates. Tauri helped with size, but Rust wasn’t a fit for everyone, and Bun was emerging as an option for a full TypeScript stack. That motivated a new framework built around Bun, with a native layer implemented in Zig, C, C++, and Objective‑C.

The post highlights the platform expansion: Electrobun started as macOS‑only but now ships first‑class support for macOS, Windows, and Ubuntu. It claims end‑to‑end packaging workflows, including installer generation, auto‑update artifacts, and differential patches. The delta updates are powered by a Zig port of bsdiff optimized with SIMD and zstd, allowing only small patch deltas to ship even when full apps are large. As Bun’s FFI matured, the framework replaced much of its custom Zig FFI layer with Bun’s built‑in capabilities; the architecture shifted so Bun could leverage shared memory when spinning up workers, keeping multi‑process workloads efficient.

Electrobun is described as “complete” in core platform features: window controls, menus, accelerators, global shortcuts, clipboard, dialogs, webview partitions, session storage, find‑in‑page, and tooling for bundling and updates. A notable technical deep‑dive is the “OOPIF story,” where the project builds a custom `<electrobun-webview>` to replace Electron’s deprecated `<webview>` tag. The goal is a “super iframe” with proper DOM positioning, process isolation, and compositing (layering) across platforms without having to patch browser engines — aiming to avoid cursor flicker and other rendering issues.

The post closes by saying co(lab) has been rewritten on Electrobun, and that v1 is now stable enough for long‑lived desktop products. The author frames Electrobun as a foundation for ambitious apps with a cross‑platform surface area but a JS/TS‑first developer experience and a small distribution footprint.

#### Comment Thread Overview
Commenters are largely enthusiastic about a Bun‑first alternative to Electron and Tauri, especially from teams that prefer TypeScript and want to avoid Rust build complexity. Several users report real‑world use, describing faster development cycles and a smoother experience for code signing and notarization. People call out typed RPC, quick local dev with Bun, and the automatic delta‑update pipeline as tangible benefits. There’s also interest from game developers who want lightweight cross‑platform packaging without a massive Electron footprint.

The most active debate is about webview choices. Some commenters argue that system webviews are inconsistent across operating systems (especially Linux) and that bundling Chromium is sometimes the more predictable path. Others note that Electrobun supports native webviews by default but allows optional CEF (Chromium Embedded Framework) when consistency matters. This leads to comparisons with Tauri and Electron: Tauri’s Rust core versus Electron’s JS runtime, and the trade‑offs between footprint size, performance, and compatibility. Another thread focuses on practical questions like installer format, binary sizes, and CI automation for notarization. Overall sentiment is positive, with cautious questions about renderer choice and distribution ergonomics.

### [Don't Trust the Salt: AI Summarization, Multilingual Safety, and LLM Guardrails](https://royapakzad.substack.com/p/multilingual-llm-evaluation-to-guardrails)
**Categories:** LLMs, AI Agents
**HN Link:** https://news.ycombinator.com/item?id=47038032
**Score:** 138 | **Comments:** 52

#### Article Summary
Roya Pakzad’s essay argues that AI summarization — especially in multilingual settings — is far more fragile and bias‑prone than most evaluation frameworks recognize. The piece begins with a critique of “executive summary” culture: summaries can be useful, but they also erase nuance, and the process of summarizing embeds values and priorities. This leads into the author’s research focus: how LLM‑generated summaries can be subtly steered by hidden policy prompts, and how this becomes a safety risk when deployed across languages.

Project 1, “Bilingual Shadow Reasoning,” illustrates the mechanism. Pakzad used GPT‑OSS‑20B in OpenAI’s red‑teaming challenge, applying customized “deliberative” (non‑English) policies to steer the model’s hidden reasoning. The example uses a human‑rights report on Iran: the same source document is summarized three ways depending on the policy language. The Farsi‑language policy shifts framing toward government narratives, downplaying executions and emphasizing sovereignty and law‑enforcement framing. The key claim is that these policy tweaks can bypass guardrails and audits because the visible output remains neutral‑sounding; the steering happens in the model’s latent reasoning and system prompts. The author notes summarization tasks are particularly vulnerable because they appear neutral while embedding selective emphasis.

Project 2 is the Multilingual AI Safety Evaluation Lab, an open‑source platform to compare model outputs across languages along six dimensions: actionability, factual accuracy, safety/privacy, tone/empathy, non‑discrimination, and access to information. The case study compares GPT‑4o, Gemini 2.5 Flash, and Mistral Small across English and Arabic/Farsi/Pashto/Kurdish in asylum‑related scenarios. Findings: non‑English responses scored materially worse for actionability (2.92 vs 3.86 out of 5) and factuality (2.87 vs 3.55) by human evaluators. An LLM‑as‑judge system inflated scores and often failed to flag disparities, sometimes hallucinating safety disclaimers that weren’t present. Safety disclaimers in English frequently disappeared in non‑English outputs; the article gives a medical‑advice scenario where Gemini refused to suggest herbal remedies in English but provided them in other languages.

Project 3 evaluates multilingual guardrails. The team converted their evaluation dimensions into guardrail policies written in English and Farsi, then tested Mozilla.ai’s guardrail tools (FlowJudge, Glider, AnyLLM with GPT‑5‑nano) on 60 asylum scenarios. Results showed 36–53% score discrepancies depending on policy language alone, with guardrails hallucinating terms and making biased assumptions about asylum seekers’ nationality while expressing unwarranted confidence. The author argues this shows that evaluation and guardrails must be a continuous pipeline: evaluation insights should directly inform policy design, and guardrails themselves require multilingual audits. The piece ends by outlining next steps: expanding the evaluation platform to voice and multi‑turn tests, adding agentic capabilities for guardrails (e.g., search‑backed factuality checks), and continuing humanitarian use‑case evaluations.

#### Comment Thread Overview
The comments focus on multilingual behavior, cultural bias, and the unpredictability of LLM tone outside English. Several people share anecdotes about Gemini and other models adopting religious phrases or culturally specific speech patterns in Arabic or French, which they interpret as evidence of training‑data skew and limited high‑quality non‑English corpora. Others counter that certain religious expressions are common in everyday speech, while still agreeing that over‑indexing on a single worldview can be problematic in assistant outputs.

Another lively thread debates constrained generation. Some commenters describe failures to get JSON‑only outputs and recommend grammar‑constrained decoding. Others argue that constrained sampling can reduce output quality, while replies claim that quality degradation is a decoder design issue rather than an inherent cost. There is also skepticism about LLM‑as‑judge systems and their tendency to over‑reward or hallucinate compliance, echoing the article’s concerns about evaluation artifacts. Overall sentiment is mixed but engaged: many agree on the need for better multilingual evaluation and guardrail testing, while debating practical mitigation strategies and the extent to which these problems can be solved with tooling alone.

### [Stoolap/Node: A Native Node.js Driver That's Surprisingly Fast](https://stoolap.io/blog/2026/02/19/introducing-stoolap-node/)
**Categories:** Databases, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47070446
**Score:** 23 | **Comments:** 18

#### Article Summary
This post announces `@stoolap/node`, a native Node.js driver for Stoolap, an embedded SQL database written in Rust. Stoolap began as a Go project, was rewritten in Rust, and is positioned as a high‑performance embedded database with features beyond SQLite. The driver uses NAPI‑RS to provide native bindings, letting JavaScript/TypeScript code talk directly to the database engine without an HTTP server or serialization layer. The author pitches the driver as a way to make Stoolap accessible to the broader Node ecosystem, which is a common entry point for application developers.

The article explains why Stoolap exists alongside SQLite. The author praises SQLite’s maturity but claims Stoolap provides MVCC transactions, a cost‑based query optimizer, parallel execution, semantic query caching, and temporal queries with `AS OF`. These features are positioned as practical, not academic: they should improve complex workloads rather than just expand the feature list.

A benchmark suite is the centerpiece. The author says they ran 53 identical SQL operations against `@stoolap/node` and `better-sqlite3` on the same machine and dataset (10,000 rows). Everything was in memory to keep the comparison controlled. Stoolap wins 47/53 tests; SQLite wins 6. The article highlights large deltas on analytic operations: COUNT DISTINCT (138x faster), complex DELETEs (122x), subqueries (64x–57x), and GROUP BY (24x), plus other subquery and window‑function cases. SQLite’s wins are concentrated on simple single‑row operations (SELECT/UPDATE by ID, single‑row INSERT, batch INSERT, simple joins), where the absolute times are already sub‑millisecond and the margin is small (roughly 1.0x–1.6x).

The performance explanation ties back to architecture: MVCC avoids reader/writer blocking in async Node workloads, the cost‑based optimizer selects cheaper plans for multi‑predicate queries, and parallel execution is done with Rayon’s work‑stealing scheduler to scale filters, joins, sorts, and distincts across cores. The post shows a familiar API (similar to better‑sqlite3) with async and sync modes, prepared statements, transactions, and named/positional parameters. It also covers file‑based persistence via WAL with configurable durability (`sync=full`, default, or `sync=none`) and background snapshots to keep the WAL bounded. The driver ships prebuilt binaries for macOS/Linux/Windows, and is currently at v0.3.1, with connection pooling and streaming queries planned.

#### Comment Thread Overview
The small HN thread is inquisitive but cautious. Several commenters ask about binary and WASM size, drawing comparisons to wa‑sqlite. Others question the fairness of the in‑memory microbenchmarks and ask for a clearer test harness, noting that SQLite’s strengths show up in persistence and real disk workloads. The author responds by adding the benchmark harness to the repo. There is also confusion about the project’s evolution (Go → Rust → Node) and whether the driver is “truly native” or just bindings to Rust. A few comments critique the blog’s tone and ask for more concrete details, while others push back on that critique.

There’s a light‑hearted sub‑thread about the name “Stoolap,” but the more substantive critiques revolve around testing methodology, binary size, and how performance will look in real applications. The overall tone is “promising, but show me the rigorous benchmarks and real‑world trade‑offs.”
