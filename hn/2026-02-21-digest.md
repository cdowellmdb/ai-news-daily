### [Turn Dependabot off](https://words.filippo.io/dependabot/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47094192
**Score:** 548 | **Comments:** 157

#### Article Summary
Filippo Valsorda argues that Dependabot is a net negative for security work because it floods developers and maintainers with low-signal updates that distract from real vulnerabilities. His core recommendation is to disable Dependabot entirely and replace it with two scheduled GitHub Actions: one that runs `govulncheck` against your codebase and another that runs CI against the latest dependency versions. The point is to keep visibility into true, reachable vulnerabilities while still detecting breaking changes early, but without letting the bot open endless PRs or trigger meaningless alerts.

He illustrates the problem with a case study from a security fix in `filippo.io/edwards25519`. A bug in `(*Point).MultiScalarMult` was fixed in v1.1.1, but almost nobody calls that method directly. Dependabot nevertheless opened thousands of PRs across the ecosystem and attached a scary CVSS score and “compatibility” warning, even on projects that only depended on the unrelated `filippo.io/edwards25519/field` subpackage. The author shows how this is a symptom of naive scanners that match only by module and version instead of understanding package boundaries and symbol reachability.

The post then walks through how the Go Vulnerability Database and `govulncheck` solve those problems. The database contains structured metadata down to the package and vulnerable symbols. `govulncheck` can use that metadata plus static analysis to decide whether your code is actually reachable from a vulnerable symbol. In his example, `govulncheck` reports zero vulnerabilities even though the module is present, because the vulnerable symbol is not reachable from the calling code. He includes concrete CLI output and a minimal GitHub Action that runs `govulncheck` on a schedule, claiming that this produces actionable alerts without the torrent of false positives.

The essay also tackles the non-security purpose of Dependabot: keeping dependencies current. Valsorda argues that updates should follow your project’s release cadence, not each dependency’s schedule, but you can still get the upside of early breakage detection by running tests against “latest” dependencies daily. For Go that means a scheduled `go get -u -t ./...` followed by tests; for npm it is an `npm update` before `npm test`. You get early warnings, but you don’t force every repo to merge tiny bumps. He adds a supply-chain twist: if you only install new versions in CI, you reduce the chance of malicious updates hitting production quickly. He suggests sandboxing CI steps (for example with gVisor) to reduce the ambient authority of GitHub Actions, turning “test against latest” into a safer canary rather than an exposure point.

Overall, the post is a call to shift from “automated PR churn” to “signal-rich vulnerability detection plus deliberate upgrade cycles.” It’s explicitly framed as both a developer productivity problem (alert fatigue and wasted time) and an ecosystem sustainability problem (maintainers drowning in irrelevant issues and PRs). The alternative the author offers is still automated, but based on reachability-aware scanning and scheduled testing rather than constant dependency bumps.

#### Comment Thread Overview
The comments are mixed but thoughtful, with the dominant thread debating whether better analysis tools (especially CodeQL) can address the noise problem without turning Dependabot off. Several commenters argue that scanners which trace dataflow and show a concrete path to a vulnerability are inherently more useful than version-only lookups, citing CodeQL as an example. Others push back that even dataflow systems still produce false positives and false negatives, invoking theoretical limits (Rice’s theorem) and practical limitations in frameworks that do implicit validation. A GitHub employee chimes in to clarify CodeQL’s capabilities, noting that the CLI is open-source and that queries can be tuned, while another commenter shares a real-world story of CodeQL flagging FastAPI handlers that were already type-validated. This becomes a mini-case study in base-rate fallacy: when a system is “almost always safe,” the remaining false positives dominate.

There’s also a recurring theme that “upgrading dependencies ≠ improving security.” Some note that new versions can introduce vulnerabilities, so automatic bumping can create churn without net gain. Others argue that keeping everyone on the same versions simplifies remediation. The thread also touches on context-aware vulnerabilities, like ReDoS alerts for npm packages used only in client code—cases where the bug is irrelevant to the deployment model but still generates noise. The overall sentiment trends skeptical of Dependabot-as-default, but not unanimous: people still want automation, just with better reachability and context. Many commenters seem aligned with the author’s suggestion to treat dependency testing and vulnerability scanning as separate, explicitly scheduled processes.

### [Andrej Karpathy talks about "Claws"](https://simonwillison.net/2026/Feb/21/claws/)
**Categories:** AI Agents, LLMs
**HN Link:** https://news.ycombinator.com/item?id=47099160
**Score:** 232 | **Comments:** 358

#### Article Summary
Simon Willison’s link post captures a mini-essay Andrej Karpathy shared about “Claws,” a term he proposes for a new layer of AI systems above classic LLM agents. Karpathy’s framing is that LLM agents were already a new layer on top of language models, and now “Claws” represent another layer on top of agents: they encapsulate orchestration, scheduling, context management, tool calls, and persistence in a more durable runtime. The concept is inspired by projects like OpenClaw and a growing ecosystem of smaller “claw” systems.

Karpathy’s specific example is a newly purchased Mac Mini intended for experimenting with these systems, which he describes as surprisingly popular at the Apple Store. His tweet highlights a tension: he is “sus” about running OpenClaw itself, but still excited by the core idea of persistent, orchestrated, agent-driven systems. He points to NanoClaw as interesting because it is small enough (~4,000 lines) to fit in a developer’s head and run in containers by default, suggesting that the “claw” trend might be manageable and auditable rather than purely opaque. He also name-drops several other projects (nanobot, zeroclaw, ironclaw, picoclaw), implying a proliferation of experiments that share a conceptual family.

Willison’s own commentary is about terminology and framing. He argues that Karpathy has a talent for coining sticky terms (referencing prior phrases like “vibe coding” and “agentic engineering”) and believes “Claw” is poised to become a term of art. Willison defines the category as personal-hardware AI agent systems that communicate over messaging protocols and can both respond to direct instructions and schedule tasks independently. He points out that the term has already attracted a shared emoji, and frames this as a growing vocabulary for the AI agent ecosystem.

The piece doesn’t go deep on implementations—it’s a short link post anchored in Karpathy’s tweet—but it does signal a shift in how practitioners are talking about long-running agent systems. If the “agent” era focused on tool use and interaction, “claws” are framed as the productionized, always-on layer that manages agent lifecycles, persistence, and orchestration. The core takeaway is less about any one project’s architecture and more about the emergence of a new class of system and a shared language for describing it.

#### Comment Thread Overview
The comment thread is lively and divided. A large set of comments focus on safety and trust: people contrast earlier fears about “giving AI internet access” with today’s enthusiasm for running agent systems on personal machines. Several commenters express concern about permissions, sandboxing, and the risk of running autonomous software that can fetch and execute arbitrary code. There’s also a thread about weaponization and governance, with commenters citing real-world debates about military AI and pointing out that “Skynet” jokes are less funny when the tech is already being built.

Another cluster of comments is skeptical about hype and framing. Some argue that “Claws” is just a new label for well-known orchestration patterns, and that the larger risk is marketing rather than technical novelty. Others defend Karpathy’s influence, saying he helps translate inside concepts for a broader audience and inevitably sparks experimentation. A number of commenters debate whether the excitement around always-on agent systems is warranted given current reliability and security practices, and suggest that containers or restrictive sandboxes should be a baseline requirement.

In short, the sentiment is mixed: curiosity and interest in the category, combined with unease about security, skepticism toward terminology inflation, and a recurring call for practical guardrails before people let “claws” run on their personal machines.

### [Index, Count, Offset, Size](https://tigerbeetle.com/blog/2026-02-16-index-count-offset-size/)
**Categories:** Coding Improvements, Databases
**HN Link:** https://news.ycombinator.com/item?id=47058584
**Score:** 110 | **Comments:** 51

#### Article Summary
This TigerBeetle post is an extended argument for a strict naming convention to reduce off-by-one errors and other indexing bugs in low-level code. The author describes a recurring problem: even with strong types, developers still make mistakes when juggling indexes, counts, sizes, and offsets—especially when code switches between typed arrays and raw byte buffers. The post proposes a convention that encodes the “unit” into variable names and uses consistent suffixes to make invalid combinations visually obvious.

The core rules are simple but strict: use `count` for the number of items, `index` for the position of a specific item, and maintain the invariant `index < count`. When working with bytes, call the number of bytes `size`, and use `offset` for the bytewise counterpart to `index`. This naming yields a precise conversion formula: `size = @sizeOf(T) * count`, and `offset = index * @sizeOf(T)`. The author explicitly avoids `length` because it is ambiguous across languages—`str::len` in Rust is byte-size, while Python’s `len` counts Unicode code points. The convention effectively makes “dimension errors” visible: a variable ending in `_size` should not be mixed with `_count`, and if you see `node_index + node_size` you can spot the bug immediately.

The post grounds this in TigerBeetle code examples. In a `NodePool` example, the author shows how `node_offset` and `node_index` make it nearly mechanical to verify that pointer arithmetic is correct. In the `ewah` decoding example, `source_index` and `target_index` advance by `_word_count` variables, and the symmetry of naming makes it easy to see whether increments and bounds are consistent. The post also notes two complementary conventions used at TigerBeetle: “big-endian naming,” where qualifiers are suffixes (`source_words`, `source_index`), and matching lengths of paired identifiers (`source` vs. `target`) to keep the code visually aligned and reduce cognitive load.

The author is careful not to oversell. This is not a silver bullet for correctness; it’s a low-cost guardrail that layers on top of types, tests, and code review. It’s aimed squarely at the class of bugs that happens when you misread your own code or accidentally combine quantities in different units. The broader message is that small, disciplined naming conventions can have outsized benefits in systems code, where a single off-by-one can yield memory corruption or data corruption that is hard to diagnose.

#### Comment Thread Overview
The thread is largely supportive and expands the naming discussion in interesting directions. Several commenters note that banning “length” and splitting it into `count` versus `size` is one of those conventions that sounds pedantic until you’ve debugged a serialization bug caused by confusing elements and bytes. A few add that the “big-endian naming” trick makes variables sort together in editors and grep, which improves navigation in large codebases. Others point out that consistent suffixing helps in code review because dimensional mismatches become visible without fully understanding the algorithm.

There’s also a historical and language-theory tangent: one commenter cites a C committee survey that chose `countof` over `lengthof` for a new operator, arguing that “length” was too ambiguous. Another debate revisits 0-based versus 1-based indexing. Some argue that 1-based indexing reduces off-by-one errors because you can express “last element” as `length` instead of `length-1`. Others push back, saying off-by-one errors come from mixing conventions, and that half-open intervals with 0-based indexing eliminate many problems. The argument becomes less about TigerBeetle’s convention and more about human reasoning and language design.

Overall sentiment is positive: many people adopt similar naming rules already, and the post gives a crisp, memorable articulation of why they help. The thread also reinforces that these conventions are most valuable in low-level or performance-critical code, where the cost of a naming mistake is high.

### [Cord: Coordinating Trees of AI Agents](https://www.june.kim/cord)
**Categories:** AI Agents
**HN Link:** https://news.ycombinator.com/item?id=47096466
**Score:** 122 | **Comments:** 64

#### Article Summary
Cord is presented as a response to a common pattern in agent frameworks: developers are forced to predefine the coordination structure (graphs, roles, handoffs) instead of letting the agent decide how to decompose work dynamically. The author reviews popular frameworks—LangGraph, CrewAI, AutoGen, OpenAI Swarm, and Claude’s tool loops—and argues that they all bake in a static coordination plan. This made sense when models were weak planners, but today’s models can identify dependencies and subproblems themselves. The question posed is: why are we still hardcoding decomposition?

Cord’s answer is a runtime that lets the agent generate a task tree as it works. You give it a high-level goal, and the root agent spawns subtasks, runs them in parallel, asks human questions when needed, and only forks a synthesis step after prerequisites complete. The blog post uses a concrete example (“Should we migrate our API from REST to GraphQL?”) and shows a tree where the agent spawns a REST audit and a GraphQL research task, then pauses for a human input about scale, and finally forks a comparative analysis before writing a recommendation. The important detail is that no workflow was predefined; the agent constructed it at runtime based on the evolving context.

The post introduces a key distinction between `spawn` and `fork`, described as a context-flow primitive. A spawned agent starts with a clean slate and only receives the results it explicitly depends on—like hiring a contractor with a specific spec. A forked agent inherits the full context of completed siblings—like briefing a teammate who needs the full backstory. This choice is independent of concurrency; both can run in parallel or sequentially. The author argues that this distinction gives the agent a more explicit handle on context management, and that models can intuitively pick the right tool when given minimal descriptions.

Under the hood, Cord is deliberately minimal: each agent is a Claude Code CLI process using MCP tools backed by a shared SQLite database. The toolset is small (`spawn`, `fork`, `ask`, `complete`, `read_tree`), while the MCP server enforces dependency resolution, authority scoping, and context injection. Humans are explicit nodes in the tree: when an `ask` node is ready, the runtime pauses for a terminal prompt and uses that answer as a result for downstream tasks. The author notes that the whole system is around 500 lines of Python and was validated through a series of tests where Claude correctly decomposed tasks, respected dependencies, and even called `read_tree()` unprompted to confirm state.

Finally, the author emphasizes that Cord is more protocol than implementation. The same coordination primitives could be implemented over Postgres for multi-machine coordination, with different LLM providers, or with human workers as nodes. The repo is presented as a proof of concept with a CLI interface and requires a Claude Code subscription. The big claim is that explicit, minimal coordination primitives plus model-driven tree generation are a better foundation for reliable multi-agent work than rigid, developer-defined graphs.

#### Comment Thread Overview
Comments are a mix of skepticism and curiosity. The top thread criticizes the writing as “LLM elevator pitch” and questions whether the `spawn`/`fork` distinction is truly novel. The author responds that the labeling is not the main innovation and acknowledges overselling, clarifying that the novelty is dynamic tree generation more than the names themselves. Another commenter proposes making “context query” a first-class primitive for compaction, suggesting a way to control how much context is passed downstream without polluting prompts.

Some readers are excited about the tree structure as a way to impose determinism on probabilistic systems, arguing that strict DAG-like coordination is the only path to reliable agent behavior. Others are fatigued by orchestration frameworks altogether, pointing to simpler tooling (like tmux-based workflows) or asking for performance evidence and real-world benchmarks. There are also comparisons to existing systems like Claude’s agent teams and TodoWrite/TodoRead patterns, with a few commenters arguing that many of these capabilities are already emerging in first-party tools.

Overall sentiment is cautious but engaged: people like the core idea of explicit dependency trees and context control, but want to see clearer proof of novelty and results beyond a proof-of-concept. The discussion is notable for its emphasis on practical ergonomics—what matters is not just decomposition, but how well the protocol scales, how it manages context, and whether it reduces or increases operational complexity for real teams.
