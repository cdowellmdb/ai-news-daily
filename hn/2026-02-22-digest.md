### [How I Use Claude Code](https://boristane.com/blog/how-i-use-claude-code/)
**Categories:** AI Agents, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47106686
**Score:** 767 | **Comments:** 488

#### Article Summary
Boris Tane describes a Claude Code workflow optimized for large, non-trivial codebases by enforcing a strict separation between planning and execution. The core principle is that Claude must not write code until a human has reviewed and approved a written plan. He argues that most failures in AI-assisted coding are not syntax bugs but architectural mismatches with the surrounding system: duplicated logic, missing caches, migrations that ignore ORM conventions, or endpoints that violate existing patterns. To mitigate this, his process begins with a “deep-read directive” where Claude must study the relevant code paths and produce a detailed `research.md`. The human uses this document as the review surface to verify that the model truly understands the system before letting it plan any changes.

Phase 1 (Research) uses deliberately emphatic prompts (“deeply,” “in great detail,” “don’t stop until you find all bugs”) to prevent superficial skimming. The research artifact is persistent, explicit, and auditable. If the research is wrong, the plan is wrong, so the workflow treats the research report as a gating step. Phase 2 (Planning) then asks for a detailed `plan.md` that includes approach, file paths, snippets, and trade-offs. Tane avoids Claude’s built-in plan mode and instead uses explicit markdown files to keep the plan editable and durable in the repo. He often provides reference implementations from other projects to ground the plan and reduce hallucinated architecture.

The distinctive step is the “annotation cycle”: the human opens the plan in their editor and adds inline notes—short corrections or longer constraints. Examples include explicit API method changes, forbidding a cache, or clarifying data model semantics. Claude is then asked to revise the plan to address every note, without implementing anything. This loop repeats multiple times until the plan reflects the real constraints and priorities that only the human knows. Once satisfied, Tane requests a granular todo list appended to the plan, turning it into a progress tracker. Only then does he issue a standardized “implement it all” prompt that encodes expectations like strict typing, continuous type checking, and marking tasks as completed.

During implementation, the human role shifts from architect to supervisor. Feedback becomes terse and precise, especially for frontend tweaks, where rapid, low-friction corrections are preferred over long explanations. He emphasizes that it’s better to revert a bad direction entirely and re-scope than to patch a flawed approach. The workflow intentionally makes implementation “boring” by front-loading creativity and decision-making into the planning and annotation phases. The payoff is less rework, fewer architectural mistakes, and better control over the system’s evolution.

Limitations are implied rather than stated: the workflow is time-intensive upfront and assumes the human can evaluate architecture choices, which may be a bottleneck. It also assumes that the model can reliably follow the “don’t implement yet” constraint and correctly translate human notes into updated plans. The benefit is a repeatable, high-signal process for complex tasks where unreviewed AI output is too risky. The overall thesis is that AI coding tools are most effective when treated as powerful executors of a human-validated design, not as autonomous designers.

### [Show HN: Llama 3.1 70B on a single RTX 3090 via NVMe-to-GPU bypassing the CPU](https://github.com/xaskasdf/ntransformer)
**Categories:** LLMs
**HN Link:** https://news.ycombinator.com/item?id=47104667
**Score:** 320 | **Comments:** 82

#### Article Summary
This project, `ntransformer`, demonstrates running Llama 3.1 70B on a single RTX 3090 by streaming model weights from NVMe directly into GPU memory, bypassing the CPU. The repository positions itself as a high-efficiency C++/CUDA inference engine with a multi-tier caching architecture and an NVMe direct I/O backend. The goal is to treat NVMe as an extension of GPU memory and avoid the CPU/RAM bottleneck when models exceed VRAM capacity.

The NVMe direct approach requires system-level changes. The repo provides `scripts/setup_system.sh` to patch NVIDIA DKMS modules, enable VFIO, bind NVMe devices to VFIO, and adjust kernel/BIOS settings (Above 4G Decoding, Secure Boot off). The approach uses GPU-initiated NVMe access: model weights are written as GGUF to a raw NVMe block device, then the GPU reads layer chunks directly via NVMe without the CPU in the data path. The README cautions about hardware risks—data loss, instability, and the need to avoid using boot drives as NVMe targets—because VFIO passthrough and low-level MMIO are involved.

Architecturally, the repo describes a 3-tier adaptive caching pipeline. Tier A keeps early layers in VRAM, Tier B uses pinned host RAM with double buffering for mid layers, and Tier C uses NVMe or mmap for overflow. The system overlaps NVMe reads, host-to-device DMA, and GPU compute. The README provides a layer-by-layer streaming description (e.g., ~670MB per layer for 70B Q6_K) and claims a large speedup from its “SLEP” layer streaming engine. It also lists supported quantization formats (Q4_0, Q4_K_M, Q5_K, Q6_K, Q8_0, F16, F32) and phase milestones: foundation (8B), single-GPU 70B with streaming, optimizations, NVMe direct backend, and a future polish phase with speculative decoding and a C API.

Key technical components include custom CUDA kernels (GEMV, RMSNorm, RoPE, SwiGLU, softmax), a GGUF model loader, an inference engine with tokenizer and sampler, and scripts for environment setup and NVMe binding. The design is explicit about trading convenience for performance: by placing NVMe in the GPU data path, it avoids CPU bottlenecks but requires careful kernel and driver manipulation. The repo is candid about the risks and the complexity of a stable setup.

The work matters because it expands the feasibility of running very large models on consumer hardware without multi-GPU setups. If robust, this enables local inference for large models without relying on cloud services or high-memory server GPUs. The limitations are substantial: the setup is complex, unsafe if misconfigured, and likely sensitive to kernel versions and driver updates. Performance depends on NVMe throughput and PCIe topology, and the overall token/sec might still be low compared to full VRAM execution. Nonetheless, it is a concrete prototype demonstrating GPU-initiated storage streaming, a technique that could become more mainstream in local LLM inference.

### [How Taalas “prints” LLM onto a chip?](https://www.anuragk.com/blog/posts/Taalas.html)
**Categories:** LLMs
**HN Link:** https://news.ycombinator.com/item?id=47103661
**Score:** 305 | **Comments:** 163

#### Article Summary
This post is a layperson-friendly exploration of Taalas, a startup claiming to run Llama 3.1 8B on a fixed-function ASIC at roughly 17,000 tokens per second using 3–6 bit quantization. The author frames the core idea as “printing” a model onto a chip: instead of repeatedly fetching weights from external VRAM/HBM like a GPU does, the model’s weights are physically embedded in the chip’s transistors. The result is a highly specialized device optimized for one model and one workload, with dramatic gains in throughput, cost, and power usage—at least in Taalas’s claims.

The article first explains the GPU inference path: each token requires sequentially loading weights for each layer, performing matrix multiplications, and writing intermediate activations back to VRAM. This back-and-forth causes latency and power draw due to the memory bandwidth bottleneck (often called the “memory wall” or von Neumann bottleneck). Taalas sidesteps this by laying out the model layers as physical circuits on silicon, so the input signal flows through the layers without repeated memory fetches. Weights are effectively ROM, and computation is embedded in the wiring.

The author notes a specific claim from Taalas: a scheme to store a 4-bit value and multiply it using a single transistor (“magic multiplier”). Details are sparse, but the implication is analog or bit-serial techniques that reduce the number of transistors per multiply. The post then explains how Taalas still uses a small amount of on-chip SRAM for the KV cache (context memory) and LoRA adapters, while avoiding external DRAM/HBM. This is positioned as a cost and complexity win because SRAM can live on the same die as logic, while DRAM typically cannot.

A key concern is flexibility: if weights are etched in silicon, the chip is non-rewritable. The author compares it to a cartridge or CD-ROM: one model per chip. Taalas allegedly mitigates this by designing a generic base chip and customizing only the top metal layers for a new model, which reduces time and cost versus a full re-spin. The post cites a reported two-month turnaround for Llama 3.1 8B. In AI timelines, that feels slow; in ASIC timelines, it’s unusually fast.

The piece concludes with cautious optimism. It’s not a deep engineering teardown; rather, it’s a conceptual bridge for software engineers trying to understand how ASICs could make LLM inference cheaper and faster. The limitations are clear: this approach trades flexibility for performance and requires significant fabrication infrastructure. It also locks a device to a specific model version, making rapid iteration or retraining expensive. Still, the post suggests that for stable, widely used models, ASIC inference could become a compelling production path, particularly for high-volume deployment where power and cost dominate.

### [Two Bits Are Better Than One: making bloom filters 2x more accurate](https://floedb.ai/blog/two-bits-are-better-than-one-making-bloom-filters-2x-more-accurate)
**Categories:** Databases
**HN Link:** https://news.ycombinator.com/item?id=47046070
**Score:** 160 | **Comments:** 22

#### Article Summary
This post from Floe’s engineering blog explains how they improved bloom filter accuracy for a database engine by using two bits per element in a cache-friendly way. The article starts with a primer: a bloom filter is a probabilistic structure that can quickly answer “definitely not in the set,” allowing false positives but never false negatives. In the context of database query processing, bloom filters let the engine avoid expensive work—like decompressing columns or probing hash tables—for values that cannot possibly match.

Floe uses bloom filters in two places: as storage-engine filters (to avoid decompressing columns that are unlikely to match) and as hash-join filters (to avoid probing the build-side hash table for keys that aren’t present). They describe an adaptive approach for storage filtering: the engine measures how many rows are rejected and can disable bloom filtering when it is ineffective (e.g., high selectivity, large build side, or skewed data). An illustrative example suggests a 9x reduction in decompression work when a bloom filter rejects 99% of rows.

For hash joins, the team uses a fixed-size bloom filter (256KB) per join to balance memory usage and CPU cache behavior. The fixed size provides predictable performance and allows compiler optimizations. However, they observed a problem: with a single-hash (k=1) bloom filter, the false positive rate rises quickly as the filter saturates. Using the standard false positive equation, they estimate ~11.5% FP at their chosen parameters (k=1, n=256K, m=2M bits), which they considered too high.

To reduce false positives without sacrificing cache locality, they experimented with alternatives and settled on a “two bits, one uint32” approach. A single hash value is split into fields: 16 bits for the array index, and two 5-bit positions within the same 32-bit word. This means each insert sets two bits in the same cache line, preserving a single memory access. The approach improves accuracy because requiring two bits to be set reduces the chance of false positives compared to a single bit, while avoiding the cache penalties of multiple independent hashes. The post discusses unsuccessful variants (two independent hashes, or two bits in separate cache lines) before motivating the final design.

The article also goes into bloom filter theory (bit occupancy, false positive rate formulas) and provides code snippets for the old and new implementations. The key takeaway is a pragmatic, performance-sensitive bloom filter design that’s fast, cache-aware, and more accurate. It’s especially relevant for analytical databases where join selectivity and scan costs dominate.

Limitations are acknowledged implicitly: the improved filter still saturates as data grows, and the fixed size is a tradeoff. The method also depends on the quality of the hash function and the particular workload; if the filter fills too much, accuracy drops regardless of the two-bit scheme. Nevertheless, the post shows how small data structure changes can yield significant performance gains in real database pipelines.

The HN discussion is technical and critical but appreciative. The dominant thread argued that the article reinvented known “blocked bloom filter” techniques, which already address cache locality by grouping bits within a block. Despite criticism, several comments praised the clarity of the math explanation and the non-intuitive nature of the two-bit improvement. ### [What Is a Database Transaction?](https://planetscale.com/blog/database-transactions)
**Categories:** Databases
**HN Link:** https://news.ycombinator.com/item?id=47110473
**Score:** 110 | **Comments:** 17

#### Article Summary
PlanetScale’s article is an interactive primer on database transactions, using step-by-step animations and session timelines to explain atomicity, isolation, and concurrency. It defines a transaction as a sequence of database operations that are executed atomically: either all changes commit or none do. The article shows how transactions begin with `BEGIN` and end with `COMMIT`, and how `ROLLBACK` reverts changes when errors or cancellations occur. It highlights that databases like Postgres and MySQL handle failures (e.g., power loss) using durability mechanisms such as write-ahead logs.

The post then explores consistent reads. A transaction should see a stable view of the database even as other transactions run concurrently. It contrasts Postgres and MySQL implementations. Postgres uses multi-version concurrency control (MVCC): updates create new row versions with `xmin`/`xmax` metadata to determine visibility. MySQL (InnoDB) uses an undo log to reconstruct prior versions because it overwrites rows directly. The article walks through example timelines of concurrent sessions to show how each system ensures isolation and when changes become visible.

Isolation levels are explained from strongest to weakest: Serializable, Repeatable Read, Read Committed, and Read Uncommitted. The article uses classic anomalies (phantom reads, non-repeatable reads, dirty reads) to illustrate tradeoffs between correctness and performance. Serializable is presented as the strictest mode, requiring transactions to behave as if run in a sequential order, often using locking or conflict detection.

A final section compares how MySQL and Postgres handle concurrent writes in serializable mode. MySQL relies on row-level locking, which can lead to deadlocks that are resolved by aborting one transaction. Postgres uses Serializable Snapshot Isolation with predicate locks that track potential conflicts without blocking reads, allowing it to detect conflicts and abort as needed without the same deadlock patterns. The article concludes by encouraging readers to experiment and points to a Discord community for further discussion.

The piece is educational rather than novel. It aims to build intuition for transaction semantics and helps engineers understand why isolation levels matter and how different engines implement them. The interactive visuals are central to the learning experience, making it easier to grasp concurrent behavior that is otherwise difficult to reason about.

### [We hid backdoors in ~40MB binaries and asked AI + Ghidra to find them](https://quesma.com/blog/introducing-binaryaudit/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47111440
**Score:** 84 | **Comments:** 29

#### Article Summary
Quesma introduces “BinaryAudit,” a benchmark for evaluating how well AI agents can detect backdoors in compiled binaries using reverse engineering tools like Ghidra and Radare2. The post explains why binary analysis is difficult: compilation erases high-level structure, aggressive optimizations obscure control flow, and symbol names vanish. The authors describe how reverse engineering usually requires translating raw bytes to assembly and then decompiled pseudo-C, a workflow that traditionally demands expert knowledge.

The benchmark setup injects backdoors into open-source projects, compiles them into stripped binaries, and asks AI agents to determine whether the binaries contain malicious modifications. The task is framed as a realistic security audit problem: backdoors are small, often only a few lines, and buried deep in large binaries. The models must identify suspicious code paths and provide concrete evidence (addresses or functions) rather than vague claims. The article highlights examples where Claude Opus 4.5 successfully found a backdoor in a modified `lighttpd2` binary by scanning for `popen()`, tracing references, and decompiling the suspicious function. The backdoor was triggered by an undocumented HTTP header and executed shell commands, returning output in another header.

The authors also document failure cases. In a modified `dnsmasq` binary with an obvious `execl("/bin/sh")` backdoor tied to a custom DHCP option, Claude Opus 4.6 found the code but rationalized it as benign, illustrating how models can talk themselves out of correct detections. The post includes detailed reverse engineering snippets and emphasizes that the task is not simply string search; it requires reasoning about control flow, data flow, and context.

Results show a tradeoff between detection and false positives. GPT-family models reportedly had near-zero false positives but low detection rates (up to ~18%). Claude Opus 4.6 detected more backdoors (up to ~46%) but with a higher false positive rate (~22%). The authors argue that end-to-end malware detection is still unreliable, but AI can lower the barrier to entry for first-pass audits and make reverse engineering more accessible.

The post concludes that AI-driven binary analysis is improving rapidly, especially with better tool integration. It suggests that model performance could improve with “context engineering,” better workflows (e.g., MCP integrations), and access to commercial tools like IDA Pro or Binary Ninja. The benchmark is positioned as a starting point for measuring real-world capability and guiding future model/tool co-design.
