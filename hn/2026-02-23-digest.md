### [Ladybird adopts Rust, with help from AI](https://ladybird.org/posts/adopting-rust/)
**Categories:** Coding Improvements, LLMs
**HN Link:** https://news.ycombinator.com/item?id=47120899
**Score:** 635 | **Comments:** 324

#### Article Summary
Ladybird’s team announces a pragmatic, staged move toward Rust for parts of the browser, motivated by memory safety and ecosystem maturity rather than a desire to rewrite everything. The post explains that they had previously evaluated Swift but found the C++ interop too limiting and platform support too Apple‑centric, while Rust’s systems ecosystem has matured and is already being adopted in Firefox and Chromium. The key tension is that the web platform’s object model is rooted in 1990s OOP patterns with inheritance and GC, which clashes with Rust’s ownership model. After a year of little progress, the project decided Rust is the most practical path forward even if it is not the perfect conceptual fit. Going forward, they will incrementally rewrite parts of the codebase in Rust, while keeping the existing C++ engine alive for a long time.

The first concrete target is LibJS, Ladybird’s JavaScript engine. They chose it because its lexer, parser, AST, and bytecode generator are relatively self‑contained and already have extensive test coverage via test262. The porting approach is notable: the author used Claude Code and OpenAI Codex as translation assistants, but stresses this was human‑directed rather than autonomous generation. The workflow was “hundreds of small prompts,” with the author deciding what to port, in what order, and what the Rust code should look like. After the initial translation, they ran several passes of “adversarial review,” asking different models to look for mistakes and bad patterns. The stated requirement was byte‑for‑byte identical output between the C++ and Rust pipelines, so the port was shaped by a strict compatibility goal rather than idiomatic Rust.

The results are concrete and quantified. The port is about 25,000 lines of Rust, completed in around two weeks, and the author estimates it would have taken months by hand. Test coverage was used as a proof of equivalence: 52,898 test262 tests and 12,461 Ladybird regression tests all passed with zero regressions. They also report no performance regressions on their tracked JS benchmarks. To validate correctness beyond tests, they ran the C++ and Rust pipelines in a lockstep browsing mode and compared outputs for every piece of JavaScript executed. As expected, the Rust code looks like it was translated from C++ because it was—register allocation and other implementation details intentionally mimic the C++ compiler to preserve bytecode output.

The post is careful about future scope. This Rust work is explicitly a sidetrack, not a complete pivot. The mainline engine will remain C++ for now; new Rust subsystems will coexist through explicit interop boundaries. Cleanup toward more idiomatic Rust is deferred until after the C++ pipeline can be retired, and contributors are asked to coordinate porting work with the core team to avoid wasted effort. The post ends with an acknowledgment that this is a controversial decision, but asserts it is the right direction for Ladybird’s long‑term health.

### [femtolisp: A lightweight, robust, scheme-like Lisp implementation](https://github.com/JeffBezanson/femtolisp)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47121539
**Score:** 54 | **Comments:** 7

#### Article Summary
Femtolisp is presented as an intentionally small, fast, and expressive Scheme‑like Lisp implementation originally born from a self‑imposed challenge: write the fastest Lisp interpreter possible in under 1,000 lines of C. The README frames the project as a “snowball” from that goal, gradually incorporating powerful features while keeping the codebase compact and understandable. Along the way, the author assembled a library of favorite C utilities to form a minimal standard library, including a custom I/O layer (`ios`) that replaces parts of C’s stdio with more flexible features. The project prioritizes a small footprint and a clear conceptual core as a design philosophy rather than a marketing claim.

The README emphasizes that femtolisp remains tiny—about 150 KB, self‑contained, and fast—while still delivering a substantial feature set expected from serious Lisp systems. The feature list includes vectors, strings, gensyms, backquote support, exceptions, and the ability to print and read circular or shared structures. It supports readable printing for all values, pretty‑printing, hash tables, and proper tail recursion. There is built‑in support for using C data types directly, described as similar in spirit to Python’s ctypes. The language includes ordered comparison predicates that work even with circular structures, plus I/O and memory streams with UTF‑8 support. Compatibility with Scheme is a goal; it is described as “highly compatible” and even includes some R6RS features.

Performance and implementation details are central to the pitch. The system includes a bytecode compiler and virtual machine. Notably, the compiler is written in femtolisp itself, and the bytecode is “first‑class,” meaning it can be printed, read, and manipulated directly. The bytecode format is intentionally human readable—encoded as low ASCII strings—so introspection and experimentation are accessible. Despite many primitives being implemented in the language itself (rather than in C), femtolisp claims to be among the fastest non‑native‑compiled Scheme implementations. The README suggests that the minimal, carefully designed core allows the system to stay fast while preserving expressive power.

The language’s conceptual model is spelled out: it is a Lisp‑1 with lexical scope. The core consists of 12 built‑in special forms and 33 built‑in functions. A primary design goal is to keep code “concise and interesting,” with each concept implemented in a single place. This is presented as both an aesthetic preference and a reliability strategy: fewer implementations means fewer opportunities for bugs. The README even references a “torture.scm” file as a demonstration of the kind of small, generically useful features the system aims to support.

Finally, the README offers a candid, opinionated perspective on Lisp implementations in general. It acknowledges the common pattern of “everyone has their own Lisp,” but argues that many implementations omit obscure yet important features that make Lisp uniquely powerful. It name‑checks things like read macros, backreferences, and properly escaped symbol names as essential. The take‑home message is that if you are going to build a Lisp, you should do it “right,” with completeness and correctness rather than merely a minimal interpreter. In that sense, femtolisp positions itself as both a tiny system and a serious one: a compact core that still respects the full expressive tradition of Lisp.

### [Pipelined Relational Query Language (PRQL)](https://prql-lang.org/)
**Categories:** Databases, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47099980
**Score:** 52 | **Comments:** 37

#### Article Summary
PRQL positions itself as a “modern language for transforming data,” essentially a pipelined replacement for SQL that compiles down to SQL dialects. The home page emphasizes readability and composability as core benefits: PRQL expresses queries as linear pipelines of transformations, where each line takes the output of the previous line. This structure is meant to make analytical queries easier to read and write, especially for people who think in terms of step‑by‑step data transformations. The language philosophy stresses a small set of powerful, orthogonal primitives to avoid the debt and complexity that SQL has accumulated over decades.

From a practical standpoint, PRQL aims to be database‑agnostic by compiling to multiple SQL dialects, which lets it sit above existing database engines and tooling. It explicitly supports embedded SQL via “s‑strings” as an escape hatch for edge cases where PRQL doesn’t yet have a construct. It also aspires to features like column lineage and type inspection, with those noted as in progress. The language is open source and states that it will remain fully open and non‑commercial. The pitch is that this compatibility approach preserves the value of the existing SQL ecosystem while offering a more expressive and maintainable authoring experience.

PRQL is explicitly focused on analytical queries—transformation, filtering, joining, sorting, grouping—rather than transactional operations like inserts and updates. That scope is part of the language’s simplification strategy: by prioritizing data transformation workflows, PRQL can keep the core smaller and more composable. The page frames this as a response to the growing complexity of analytical workloads and the need for higher‑level abstractions that data engineers and analysts can share.

The project also highlights tooling and integrations that demonstrate maturity beyond a prototype. There is an online playground for live compilation to SQL, and a CLI compiler (`prqlc`) written in Rust with installation options via Cargo, Homebrew, and Winget. There are bindings for Python, JavaScript, and R, and references to work in other languages. Integrations include native support in ClickHouse (via setting the SQL dialect), a DuckDB extension, a Jupyter/IPython cell magic (via pyprql) that can even stand up a local DuckDB instance from a Pandas DataFrame, plus a Visual Studio Code extension for syntax highlighting and live SQL compilation. There are also mentions of Postgres functions, Databend support, and a workflow integration with Prefect.

The page’s “principles” section frames the design as pipelined, simple, open, extensible, and analytical. “Extensible” covers explicit versioning to avoid breaking changes, plus the ability to embed SQL. “Open” emphasizes community governance and interoperability. “Simple” emphasizes minimizing redundant constructs and keeping query expression direct. These principles serve as both a design philosophy and a signal to tool builders: PRQL wants to be a stable, machine‑readable target for downstream tooling as much as it is a human‑friendly language.

In summary, PRQL is a language‑level attempt to modernize how people write analytical queries without abandoning the SQL ecosystem. It doesn’t try to replace databases, but to provide a clearer, more composable syntax that compiles into the SQL dialects those databases already understand. The overall positioning is that PRQL can improve readability and developer ergonomics while retaining the deployability and compatibility of traditional SQL workflows.

### [Crawling a billion web pages in just over 24 hours](https://andrewkchan.dev/posts/crawler.html)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47117886
**Score:** 94 | **Comments:** 33

#### Article Summary
This post is a detailed, numbers‑forward retrospective on a personal challenge: crawl ~1 billion web pages in roughly 24 hours on a few‑hundred‑dollar budget. The author reports the final results up front: 1.005 billion pages in 25.5 hours for about $462. The experiment was intentionally constrained for comparability with historical crawls (notably a 2012 Michael Nielsen reference). Key constraints included a 24‑hour time limit, a small budget, and an HTML‑only approach that does not execute JavaScript—requests were made directly and links were extracted from `<a>` tags. The author also prioritized politeness: obeyed robots.txt, used a user agent with contact info, limited crawling to a seed list of top domains, enforced a 70‑second per‑domain delay, and maintained an exclusion list for opt‑outs. The crawl’s goal was to sample the web at scale rather than construct a perfect index.

The architecture is intentionally different from the “textbook” distributed crawler design. Instead of separate pools for fetchers, parsers, and storage, the system uses a dozen high‑powered, fully‑self‑contained nodes, each responsible for a shard of domains. The author’s rationale is pragmatic: they started with single‑node optimization and only scaled out once vertical scaling plateaued. Each node includes a Redis instance that stores crawl state: per‑domain frontiers (URL lists), a time‑ordered domain queue for politeness scheduling, visited‑URL records, and a bloom filter to avoid re‑adding already‑seen URLs to frontiers. Domain metadata (robots.txt, exclusions) and a parse queue of fetched pages are also held in Redis. Fetchers pop domains, fetch the next URL, and push HTML into the parse queue; parsers extract links and write back to frontiers.

Concurrency is achieved via asyncio‑based worker pools. Fetchers are highly concurrent (6,000–7,000 async workers per process) and are CPU‑bound rather than network‑bound; parsers run fewer workers (80) because HTML parsing is CPU heavy. Parsers also write truncated content to disk. The author rejected S3 due to per‑request and storage costs; at a 250 KB average page size, the implied storage would be ~250 TB, and even a single day of S3 storage would dwarf the target budget. Instead, they used storage‑optimized AWS instance storage and truncated pages at 250 KB. Compression was considered but deferred due to time.

Performance bottlenecks were different from a decade ago. Parsing, not bandwidth, became the main limit. The author discovered that modern pages are larger (median around 138 KB uncompressed in their sample) and that `lxml` parsing was too slow. Switching to `selectolax` (Lexbor‑based) and truncating pages significantly improved throughput. With these optimizations, a single parser process could handle roughly 160 pages/sec, and a full node with 9 fetchers and 6 parsers reached about 950 pages/sec. DNS and bandwidth were not limiting due to the seed list of top domains and modern datacenter bandwidth, but SSL handshakes became a surprising CPU‑heavy cost (~25% of CPU time) because the web is now overwhelmingly HTTPS.

Operationally, the biggest issue at scale was memory pressure from huge frontiers on extremely link‑dense domains. The in‑memory frontier design led to runaway memory usage for sites like Yahoo and Wikipedia, and the author had to restart nodes, truncate frontiers, and add problematic domains to the exclusion list. Fault tolerance was good enough to resume after failures, and the author accepts some URL loss because the crawl is intended as a sample. The post closes with reflections on theory vs. practice: interview‑style architectures differ from the chosen design, and real‑world issues like frontier growth, parsing costs, and SSL overhead dominate at scale. Overall, the write‑up offers a concrete recipe for high‑throughput crawling under strict cost constraints and highlights how modern web realities shift the bottlenecks compared to earlier eras.
