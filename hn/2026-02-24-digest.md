### [Goodbye innerHTML, Hello setHTML: Stronger XSS Protection in Firefox 148](https://hacks.mozilla.org/2026/02/goodbye-innerhtml-hello-sethtml-stronger-xss-protection-in-firefox-148/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47136611
**Score:** 201 | **Comments:** 85

#### Article Summary
Mozilla’s Firefox 148 release introduces the standardized Sanitizer API and a new `setHTML()` method that performs HTML sanitization at insertion time, positioned as a safer default replacement for `innerHTML`. The post frames the change around XSS remaining one of the most common web vulnerabilities and notes that historically, XSS has sat near the top of vulnerability rankings for years. Firefox has long pushed protective standards, like Content Security Policy (CSP), but CSP adoption and the architectural changes it requires have limited its coverage. The Sanitizer API is presented as a pragmatic middle ground: a browser-native, standards-based way to remove dangerous elements and attributes from untrusted HTML while keeping “safe” markup. Firefox 148 is described as the first browser to ship the standardized API, with an expectation that others will follow.

The article walks through a simple example: `setHTML()` accepts HTML but removes unsafe nodes (such as an injected `img` with an `onclick` handler) before inserting into the DOM. Developers who want to accept richer or looser HTML can supply a custom policy to specify which tags and attributes are allowed. Mozilla emphasizes that this brings safety “by default” with minimal code changes: switching from `innerHTML` assignments to `setHTML()` yields an immediate improvement in XSS posture without requiring a separate sanitizer library. The post also highlights the Sanitizer API playground as a way to experiment with policy choices before adopting it in production.

A key technical detail is the suggestion to combine the Sanitizer API with Trusted Types. Trusted Types already centralize and constrain how HTML strings are injected; once `setHTML()` is adopted, sites can enforce Trusted Types more easily and block other dangerous HTML insertion methods, reducing the likelihood of future XSS regressions. The article positions this as an incremental upgrade path: you can start by replacing `innerHTML`, then tighten enforcement with Trusted Types policies. Firefox 148’s support for both the Sanitizer API and Trusted Types is framed as an important advance that lowers the need for specialized security teams to prevent XSS.

The post’s limitations are implicit but important. Sanitization still requires correct policy choices, and the default policy may be too strict or too permissive for certain apps. The safety of the API also depends on broad cross-browser adoption; for now, Firefox is first. Finally, the move does not eliminate XSS risks across all vectors—developers still need to ensure other injection surfaces and unsafe APIs are avoided. Still, the direction is clear: make safe HTML insertion a standard, “safe-by-default” browser primitive, and reduce reliance on ad-hoc string sanitizers.

#### Comment Thread Overview
The comment thread is largely supportive of safer HTML insertion but skeptical of how developers will interpret and use multiple APIs. Several commenters worry about a mixed ecosystem of “safe” and “unsafe” methods with ambiguous names, arguing that security-sensitive APIs should be unmistakable, or that teams should ban `innerHTML` via linting so it becomes socially unacceptable (similar to how `var` fell out of favor). A recurring theme is distrust of sanitizers in general—there’s a long history of bypasses—paired with cautious optimism that a browser-native Sanitizer API might be harder to exploit because it uses the same parser as the renderer, potentially mitigating mutation-XSS edge cases that arise from parse/serialize mismatches.

There’s a side discussion about SVG and “weird” HTML parsing rules: some commenters point out that inline SVG is a common source of sanitizer escapes, and recommend avoiding inline SVG from untrusted sources entirely or serving SVG only via `<img>` to reduce attack surface. Others discuss the role of Trusted Types and ask whether they already provide a global switch to disallow unsafe HTML insertion, noting that Trusted Types enforcement plus `setHTML()` could make a clean migration path. There’s also debate over the utility of `setHTMLUnsafe`—some argue it’s helpful as a clearly labeled escape hatch for legacy patterns, while others think `innerHTML` is already familiar enough to convey the risks.

Overall sentiment: cautiously positive. People like the direction and the browser-led approach, but they emphasize that naming clarity, migration tooling, and developer behavior will determine real-world impact. The strongest counterpoints focus on the “hard part” being policy design and adoption, not the API itself.

### [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue)
**Categories:** Databases, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47099401
**Score:** 108 | **Comments:** 34

#### Article Summary
Turbopuffer describes rebuilding its internal indexing job queue around a single JSON file stored on object storage. The queue is not in the write path; it exists to notify indexing nodes that new data has landed in the WAL and that async indexing work should run. The previous design sharded queues across indexing nodes, which meant a slow node could stall work even when other nodes were idle. The replacement design uses a shared `queue.json` file and a stateless broker, yielding FIFO execution, at-least-once guarantees, and ~10× lower tail latency for queued jobs.

The article is structured as a progression of increasingly capable designs. Step 1 is the simplest possible queue: a single `queue.json` file containing job state. Pushers append new jobs and workers claim the first unclaimed job using compare-and-set (CAS) writes on object storage. CAS provides atomicity without explicit locks: a write only succeeds if the file has not changed since it was read, otherwise the client retries. This works well at very low rates (up to ~1 request/second, bounded by GCS limits) and is production-grade for small workloads.

Step 2 introduces group commit to overcome object storage write latency (up to ~200ms per write). By buffering multiple requests in memory and writing them as a batch when the previous write completes, throughput becomes limited by network bandwidth rather than latency. This mirrors the same batching pattern turbopuffer uses for WAL writes. However, contention remains: with many clients, CAS forces serialized writes, so the system still caps out at ~5 writes/sec and hits object-store limits.

Step 3 removes contention by inserting a stateless broker that performs all object-store writes. Clients send requests to the broker; the broker buffers and performs group commits on their behalf. Importantly, it only acknowledges a write after it has landed in object storage, so durability guarantees remain. Because writes are small, a single broker can handle many clients while object storage handles the heavy I/O.

Step 4 adds high availability. If a broker dies, clients detect slow responses and spin up a new broker, writing its address into `queue.json`. CAS correctness handles brief overlap between brokers. Workers also send periodic heartbeats; if a job’s heartbeat is stale, another worker can reclaim it, enabling at-least-once processing with failover.

The article concludes that robust distributed coordination can be built from a few object-store primitives. The design parallels turbopuffer’s broader architecture (object storage + memory/SSD caches), and leverages object storage for simplicity and scalability. The tradeoffs are clear: object storage has high latency and low write throughput, but predictable behavior and strong consistency that can be composed with careful buffering and minimal stateful services.

#### Comment Thread Overview
Comments are mostly appreciative of the “simple primitives, strong guarantees” approach, with a recurring theme that object-storage–based designs feel like modern variants of Delta Lake / manifest + CAS patterns. One top comment notes that using a CAS-managed manifest with buffered objects and occasional compaction can yield extremely fast read/write performance for many workloads while staying conceptually simple. Another commenter mentions their own high-throughput setup (~40k writes/sec) with similar patterns, suggesting that practical performance can exceed expectations when sharding or partitioning is introduced.

Several replies explore alternative designs to reduce contention further. One suggestion is to split job states into separate prefixes or directories (e.g., unclaimed vs. in-progress vs. done) and rely on atomic object rename primitives to simplify coordination; the idea is to avoid the “single hot object” by distributing job transitions across many objects. Others suggest naive sharding: if a queue gets hot, create a second queue for a subset of jobs or namespaces, even if that sacrifices strict global ordering.

There’s also the standard “object storage as log/queue” comparison: someone mentions WarpStream (a Kafka-compatible system that runs on S3) and reports good results after switching, reinforcing the idea that object storage can substitute for traditional brokers in the right workload. The overall tone is positive but practical—people agree the design is compelling for workloads where simplicity and predictable scaling matter more than ultra-low latency or exactly-once semantics.

### [Show HN: enveil – hide your .env secrets from prAIng eyes](https://github.com/GreatScott/enveil)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47133055
**Score:** 154 | **Comments:** 90

#### Article Summary
ENVeil is a developer tool designed to prevent plaintext `.env` secrets from being exposed to AI coding tools (or other accidental readers) by keeping the real secret values in an encrypted local store instead of on disk. The README argues that AI tools like Claude Code, Copilot, and Cursor can read project files, turning a plaintext `.env` file into an unintended secret dump. ENVeil’s solution is to store secrets in a per-project encrypted store and make `.env` files contain only symbolic references using a custom `ev://` URI scheme. At runtime, ENVeil injects the real secrets into the subprocess environment so application code sees normal environment variables.

The workflow is straightforward. Install the CLI (via `cargo install enveil` or build from source; Rust 1.70+ required), then run `enveil init` in a project to create a `.enveil/` directory with config and an encrypted store. That directory is meant to be added to `.gitignore`. You add secrets with `enveil set <key>` (values are entered interactively, not via CLI args), and reference them in `.env` like `DATABASE_URL=ev://database_url`. When you run your app with `enveil run -- <command>`, ENVeil loads the encrypted store, resolves `ev://` references, and sets those values in the subprocess environment before executing the command.

The design emphasizes minimizing leakage vectors. ENVeil deliberately does not offer `get` or `export` commands, avoiding accidental plaintext output to stdout or logs. Values can’t be passed on the command line, preventing secrets from appearing in shell history or process listings. A `list` command shows only key names; `delete` removes entries; `import` can convert a plaintext `.env` into `ev://` references; `rotate` re-encrypts the store under a new master password. The store itself is a binary blob encrypted with AES-GCM; the README highlights that a fresh nonce is generated on every write, and any tampering causes authentication failures. The project includes automated tests for the security invariants (e.g., no plaintext on disk, nonce rotation) and a manual inspection recipe using `xxd` and `strings`.

Overall, ENVeil is positioned as a pragmatic, self-contained way to mitigate a specific risk: accidental reading of secret values from `.env` files by AI tools or other software that can scan the project directory. It does not attempt to be a general-purpose secret manager or address runtime exfiltration; it simply keeps secrets off disk and out of readable files during development workflows.

#### Comment Thread Overview
The HN discussion is supportive but grounded in a clear threat-model debate. The top comments point out that `.env` files are only one of many leakage vectors: secrets often show up in logs, stack traces, database connection strings, OAuth debug output, or CI artifacts. In that sense, ENVeil is viewed as a helpful mitigation for accidental file reads but not a full solution. Several commenters emphasize that if an AI agent can run code, it can simply call `os.environ` or print process environment variables, so hiding plaintext files doesn’t prevent intentional exfiltration—sandboxing and isolation are required for that.

A thread dives into proxying and network controls as a complementary defense. There’s discussion of running AI agents behind a transparent proxy or MITM setup, with custom CA certificates injected into the container so outbound requests can be inspected or blocked; this is suggested as a way to close DNS or HTTP-based exfiltration channels. The conversation touches on how this interacts with SSL/TLS and the operational complexity of provisioning trusted certs for agent runtimes.

Sentiment is mixed but constructive. People like the idea of keeping plaintext secrets off disk—especially in AI-assisted workflows—yet they stress that security is about layers. The community’s consensus seems to be that ENVeil is useful for “accidental leak” scenarios, but must be paired with runtime isolation, logging discipline, and policy controls to meaningfully address broader exfiltration risks.

### [Steerling-8B: The First Inherently Interpretable Language Model](https://www.guidelabs.ai/post/steerling-8b-base-model-release/)
**Categories:** LLMs
**HN Link:** https://news.ycombinator.com/item?id=47131225
**Score:** 272 | **Comments:** 81

#### Article Summary
Guide Labs announces Steerling-8B, an 8B-parameter language model designed for inherent interpretability. The headline claim is that the model can trace every generated token to three sources: input context, human-understandable concepts, and the training data that drove the output. The team reports training on 1.35T tokens, yet achieving performance within range of models trained with 2–10× more compute. They release model weights, companion code, and a PyPI package for interaction.

Steerling’s architecture is built on a causal discrete diffusion model that allows steering across multi-token spans rather than only next-token prediction. The core design decomposes the embedding space into three pathways: roughly 33K supervised “known” concepts, ~100K “discovered” concepts learned by the model, and a residual channel that captures remaining information. They impose training objectives that route prediction signals through the concept pathways without sacrificing performance. The concepts feed into logits through a linear path, so each prediction decomposes into explicit per-concept contributions that can be edited at inference time—enabling concept-level steering, attribution, and alignment interventions without retraining.

The post highlights an interactive explorer that allows users to click on output chunks and see which input tokens, concepts, and training data sources contributed. This supports use cases like training data provenance, interpretability audits, and “alignment via concept control,” where explicit concept-level adjustments replace large sets of safety training examples. Benchmarks are presented to show competitiveness: Steerling reportedly outperforms LLaMA2-7B and DeepSeek-7B on average while using fewer FLOPs. A specific interpretability metric claims that over 84% of token-level contribution comes from the concept module on a held-out validation set, and that removing the residual pathway only minimally impacts LM Harness task performance—evidence that the model’s predictive signal flows through interpretable concepts. They also report 96.2% AUC for detecting known concepts in text.

The authors frame this as a foundation for deeper interpretability work: upcoming posts will detail concept discovery, concept steering, alignment without fine-tuning, and training-data valuation. The post’s implicit caveat is that interpretability hinges on the quality and semantics of the concept space; it remains to be seen how robust attribution is under adversarial or ambiguous prompts, and how well provenance maps to legal or licensing requirements. Still, Steerling positions interpretability as an architectural feature rather than a post-hoc add-on.

#### Comment Thread Overview
The thread mixes excitement with skepticism about what “attribution” and “interpretability” really buy in practice. One early comment imagines future coding agents producing an `ATTRIBUTION.md` file listing sources for generated code; replies push back that humans don’t document every source they read, sparking a broader debate about whether software should be held to different standards than humans or whether model outputs create unique legal and economic risks. Another line of discussion questions whether “alignment” is inherently desirable, arguing that alignment can be seen as pruning interesting behavior; responses push for clearer definitions of what is being aligned and to what.

Skeptical commenters probe the provenance claims: if a model can explain a token by pointing to training data, is that genuinely grounding, or is it just another confidence-weighted attribution that could be wrong when the model is wrong? The concern is that provenance could become a sophisticated version of “vibe matching” rather than proof of source. Supporters counter that if the model’s architecture routes signal explicitly through concepts, that’s meaningfully different from post-hoc attention explanations, and could enable more reliable control.

Overall sentiment is curious but cautious. People are interested in the possibility of concept-level steering and data provenance, but they’re looking for empirical validation: how reliable are attributions under adversarial prompts, how do legal/ethical norms change if models can cite sources, and does interpretability actually reduce harmful or incorrect outputs in deployment?

### [Making Wolfram Tech Available as a Foundation Tool for LLM Systems](https://writings.stephenwolfram.com/2026/02/making-wolfram-tech-available-as-a-foundation-tool-for-llm-systems/)
**Categories:** LLMs, AI Agents
**HN Link:** https://news.ycombinator.com/item?id=47129727
**Score:** 256 | **Comments:** 140

#### Article Summary
Stephen Wolfram argues that LLMs are impressive but inherently limited: they are broad and human-like, but not precise or computation-heavy. The solution, he claims, is to pair foundation models with a “foundation tool” that provides exact computation and structured knowledge. Wolfram positions the Wolfram Language and the company’s decades-long computational stack as that tool, emphasizing its breadth across algorithms, methods, and data. The moment is framed as a convergence: LLMs are mature enough to call general-purpose computational tools, and Wolfram’s technology is now accessible in a standard way for LLM systems.

The central technical concept is computation-augmented generation (CAG). Unlike retrieval-augmented generation (RAG), which injects retrieved documents into the prompt, CAG injects on-the-fly computational results into the generation stream. Wolfram describes CAG as an “infinite extension” of RAG: rather than retrieving fixed documents, the system can generate unbounded precise content via computation. The article notes that CAG is internally complex but now packaged to integrate easily with existing LLM workflows.

Wolfram announces three productized access methods, all built on CAG. First, an MCP Service allows any MCP-compatible system to call Wolfram tech via a web API, with an option to use a local Wolfram Engine. Second, the Agent One API provides a “universal agent” that combines an LLM foundation model with Wolfram tools, offering a drop-in replacement for traditional LLM APIs. Third, CAG Component APIs expose fine-grained access to specific Wolfram capabilities, enabling optimized, custom integration at any scale, with both hosted and on-premise deployment options.

The practical implication is a standardized route for LLMs to access high-precision computation (symbolic math, data, algorithms) and structured knowledge. The article frames this as a step toward deeper alignment between LLM pretraining and external computational tools. Limitations are not deeply explored, but the reader can infer tradeoffs: integration complexity, potential cost and dependency on the Wolfram stack, and the need to verify that CAG outputs are used appropriately in downstream generation. Still, the post makes a clear product and ecosystem bet: precise computation should be a first-class tool alongside general-purpose foundation models.

#### Comment Thread Overview
The HN discussion broadens quickly from tooling to economics and incentives. A prominent thread debates funding models: commenters note that open source and academic work often rely on unpaid or underpaid labor, arguing that “people need to eat,” and that a hobby-funded model can slow progress—especially if AI is poised to displace labor at scale. This ties into a recurring theme: if society funded AI research with public money, should society receive a larger return on investment? Others counter that software is effectively post-scarcity, so different economic rules should apply compared to physical lab equipment.

There’s also philosophical discussion about the value of commercial tools vs. open alternatives. Some commenters argue that Wolfram’s approach is the logical path to operationalize precise computation within AI systems, while others worry that proprietary stacks could limit accessibility or lock in dependencies. Several comments riff on “software as blueprint” vs. “execution as machine,” reinforcing the idea that computation-as-a-service is distinct from open code distribution.

Overall sentiment is mixed: respect for Wolfram’s long-term vision and the engineering depth of the stack, balanced against concerns about commercialization, incentives, and how the benefits of AI + computation will be distributed. The thread doesn’t dispute the utility of tool-augmented LLMs; rather, it questions the economic and governance implications of how those tools are packaged and who controls them.

### [Car Wash Test on 53 leading AI models](https://opper.ai/blog/car-wash-test)
**Categories:** LLMs, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47128138
**Score:** 326 | **Comments:** 385

#### Article Summary
Opper’s “Car Wash” test evaluates whether LLMs can answer a deceptively simple reasoning question: “I want to wash my car. The car wash is 50 meters away. Should I walk or drive?” The correct answer is “drive” because the car itself must be at the car wash. The article treats this as a minimal logic benchmark and runs it across 53 models via Opper’s gateway, with no system prompt and a forced choice between “walk” or “drive” plus a reasoning field. The test is executed in two phases: a single run per model, then a 10-run consistency test per model (530 total calls).

Results are stark. In the single-run test, only 11 of 53 models answered correctly; 42 said “walk.” The models that passed included Claude Opus 4.6, Gemini 2.0 Flash Lite, Gemini 3 Flash, Gemini 3 Pro, GPT‑5, Grok‑4, Grok‑4‑1 Reasoning, Sonar, Sonar Pro, Kimi K2.5, and GLM‑5. The article notes that most failures focused on “50 meters is short, walking is better,” missing the core requirement that the car must be present. Even correct answers sometimes came with bizarre reasoning: Sonar and Sonar Pro, for example, cited EPA studies about calorie emissions to justify driving.

The 10-run consistency test shows reliability is worse than a one-off success suggests. Only five models answered correctly 10/10 times (Claude Opus 4.6, Gemini 2.0 Flash Lite, Gemini 3 Flash, Gemini 3 Pro, Grok‑4). GPT‑5 scored 7/10, implying a 30% error rate on an extremely simple question. Many models dropped to coin‑flip or worse. The author highlights that “flukes” are common—models that answered correctly once could fail repeatedly when rerun.

To calibrate against humans, Opper partnered with Rapidata to run the same forced-choice question with 10,000 people. 71.5% answered “drive,” which the article uses as a baseline: only the top five models and a couple of near‑perfect models surpassed average human performance. The piece argues that the failure mode is heuristic dominance rather than lack of capability, and suggests “context engineering”—providing structured examples or domain cues—as a way to push models toward reasoning over heuristics. A separate experiment is cited where a small model with curated context matched a frontier model at dramatically lower cost. The article publishes full results and raw JSON for reproducibility.

The limitations are inherent to the setup: a single, trick‑like prompt with a forced choice may not reflect real‑world tasks, and model behavior can shift with even small prompt changes. Still, the test exposes a reliability gap that matters for production use, where consistent correctness is more important than occasional brilliance.

#### Comment Thread Overview
The discussion focuses on evaluation methodology and what the test actually measures. Some commenters praise the inclusion of a 10,000‑person human baseline and the publication of raw data, but others ask for the full evaluation set or suggest expanding beyond a single trick question. There’s debate over framing sensitivity: a few commenters argue that the test probes “distributional priors” more than reasoning, and suggest that prefacing the prompt as a trick question might shift results. Others counter that in practice, users care about whether the model can do the task, not whether it passes a philosophical definition of reasoning.

Several replies dissect the human baseline result (71.5% drive). Some note that the number aligns with other “default bias” effects (like cookie consent ratios), while others point out that humans also fail nontrivially—suggesting the benchmark is hard in a subtle way. Another thread questions which model ChatGPT defaults to, and whether comparisons should be made against GPT‑5 or the default variant.

Overall sentiment is mixed but engaged. People appreciate the clarity of a simple benchmark, yet caution against over‑generalizing. The most common request is for more tasks and for controlled prompt variations to tease apart “reasoning” from “prompting artifacts.” The community seems to agree that the consistency results are the most damning: even models that answer correctly once can be unreliable, which is the real risk in production settings.

### [Writing code is cheap now](https://simonwillison.net/guides/agentic-engineering-patterns/code-is-cheap/)
**Categories:** AI Agents, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47125374
**Score:** 308 | **Comments:** 377

#### Article Summary
Simon Willison’s essay argues that agentic coding tools invert long‑standing assumptions about software engineering. Historically, writing code has been expensive: developers spend days producing a few hundred clean, tested lines. That scarcity shaped both macro‑level practices (planning, estimating, prioritizing) and micro‑level decisions (refactoring vs. shipping, writing tests vs. skipping, documenting edge cases vs. moving on). Agentic tools dramatically reduce the cost of producing code, and parallel agents amplify this by letting a single engineer run multiple implementation efforts at once. The result is a shift in how we should evaluate tradeoffs.

The key point is that while “code typing” is cheap, “good code” is not. Willison defines “good code” as code that works, is verified, solves the right problem, handles error cases, remains simple and minimal, is backed by tests, is documented, and is designed for future change without over‑engineering. He emphasizes that non‑functional qualities—reliability, security, maintainability, observability, usability—remain costly. Agents can help with many of these, but they don’t remove the burden of human judgment and verification.

The essay suggests that the real challenge is habit change. Engineers and organizations are used to filtering ideas by “is it worth the time to code?” That filter no longer applies when code generation is cheap. Willison’s tentative guidance is to second‑guess that instinct: if an idea seems not worth the time, try it anyway via an asynchronous prompt; the worst outcome is a short wasted experiment. The larger goal is to develop new practices for agentic engineering, where experimentation is cheap but evaluation, testing, and integration remain expensive.

The piece is deliberately early and exploratory. Willison notes that the industry is still figuring out best practices, and he positions this as one chapter in a broader guide on agentic engineering patterns. It’s less a prescription and more an invitation to rethink where costs really live in software development. The implicit limitation is that the guidance is high‑level; translating this into concrete processes, budgeting, and quality gates remains an open problem.

#### Comment Thread Overview
The thread mostly expands on the economics of software rather than disputing the core idea. One top‑level comment argues that people misunderstand the intrinsic value of “writing code,” pointing out that code’s cost has always been embedded in broader organizational and maintenance overhead. Replies emphasize that if code ever seemed cheap, it was because costs were hidden elsewhere: outages, data corruption, operational mistakes, tech debt, and coordination failures. Several commenters stress that LLMs lower the short‑term cost of producing working code but may increase long‑term costs by expanding the surface area that must be maintained, tested, and secured.

A recurring theme is process vs. production. Some argue that heavy testing, multi‑platform validation, or layered approvals can dwarf the cost of typing, and that the bottleneck is increasingly “process” rather than code. Others caution against swinging too far: not every change needs exhaustive validation, but under‑investing in quality will amplify the long‑term costs of maintenance. There’s also debate about whether agentic tools change the fundamental economics or just shift where the expense lands—toward review, QA, and coordination.

Sentiment is reflective rather than polarized. Many agree with Willison’s premise that “good code is still expensive,” but they want empirical data to understand the net effect on total cost of ownership. The discussion suggests that agentic tooling will force organizations to make explicit tradeoffs about quality and speed, rather than assuming coding time is the primary constraint.
