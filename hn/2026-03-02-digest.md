### [Anthropic Cowork feature creates 10GB VM bundle on macOS without warning](https://github.com/anthropics/claude-code/issues/22543)
**Categories:** AI Agents, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47218288
**Score:** 194 | **Comments:** 81

#### Article Summary
This post is a high-priority performance bug report in Anthropic’s `claude-code` repository documenting a serious local resource issue tied to Claude Cowork on macOS. The reporter says Cowork creates a virtual machine disk image (`rootfs.img`) under `~/Library/Application Support/Claude/vm_bundles/claudevm.bundle/` that grows to roughly 10GB and does not get cleaned up automatically. The report is more than “disk is large”: it also includes before/after cleanup observations, CPU behavior over time, and swap activity trends, pointing to two likely problems happening simultaneously: storage growth and runtime degradation.

The key technical evidence in the issue is practical and reproducible. The reporter deleted `vm_bundles`, `Cache`, and `Code Cache`, shrinking local Claude storage from about 11GB to 639MB and seeing an immediate ~75% performance improvement in tasks that previously hung or failed. But performance then degraded again over minutes, with idle CPU rising from around 24% after restart to around 55% during use (renderer/main/GPU process breakdown included), and swap-ins climbing steadily. That distinction matters: deleting bundle/cache files gives short-term relief but may not fix the underlying runtime accumulation behavior.

Anthropic labels the issue `bug`, `high-priority`, `oncall`, and `performance`, which suggests internal triage urgency. In HN comments, an Anthropic engineer (Felix Rieseberg) adds architecture context: Cowork runs Claude Code’s agent harness inside a Linux VM using Apple’s virtualization framework on macOS (and Host Compute System on Windows), with extra sandboxing/network/filesystem controls. The stated rationale is clear: give the agent a separate machine-like environment with stronger boundary guarantees instead of letting it operate directly on the user’s host system.

Why this matters: it exposes an important tradeoff in agentic tooling. VM-backed isolation can improve safety guarantees and reproducibility, but unless lifecycle management is excellent (cache/bundle cleanup, memory pressure control, process idle behavior), users on constrained hardware (8GB RAM in this case) can experience severe degradation. That directly affects developer trust and day-to-day usability, especially for “always-on” assistants.

Limitations and open questions remain unresolved in the report: whether the root cause is primarily VM image retention policy, memory leak-like behavior in desktop processes, runaway background work, or a combination; whether degradation differs by workload type; and what long-term fix strategy Anthropic will ship (bundle GC, process tuning, telemetry-driven leak fixes, or architecture changes). For now, the workaround is manual cleanup and periodic restart.

#### Comment Thread Overview
Sentiment is mixed but highly technical: people appreciate the transparency of the report and Anthropic’s direct response, while also expressing skepticism about heavyweight local agent architectures. The most useful discussion centers on architecture and operations, not just complaints.

One major thread is “why a VM at all?” Anthropic’s explanation (isolation and stronger guarantees) was generally treated as credible, but commenters pushed on cost: disk growth, CPU overhead, and poor behavior on low-memory machines. A second thread focuses on practical mitigation and diagnosis tools. Commenters suggest utilities like `ncdu` and DaisyDisk for locating disk growth quickly, while others caution that random tool recommendations in viral threads can be risky for less technical users.

A recurring counterargument is trust and control: several people argue agent vendors should minimize host footprint and make cleanup/retention behavior explicit, especially when products run persistent background infrastructure. There are also first-hand “same class of issue” anecdotes from users seeing performance decay over long sessions with AI coding tools, reinforcing that this is not viewed as an isolated papercut.

Overall, commenters treat the issue as a real signal about agent UX maturity. The constructive consensus is that VM isolation can be the right design, but only if paired with robust lifecycle management, predictable resource ceilings, and clearer user-facing controls.

### [How I run 4–8 parallel coding agents with tmux and Markdown specs](https://schipper.ai/posts/parallel-coding-agents/)
**Categories:** AI Agents, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47218318
**Score:** 20 | **Comments:** 1

#### Article Summary
This article is a workflow write-up for running multiple coding agents in parallel without a heavyweight orchestration framework. The author’s core claim is that a lightweight stack (tmux, markdown specs, shell aliases, and a small slash-command system) is enough to coordinate 4–8 concurrent agents productively, provided planning discipline is strong.

The central artifact is a “Feature Design” (FD) markdown file per change. Each FD captures problem definition, options considered with tradeoffs, selected implementation plan (including target files), and verification steps. The author reports having created 300+ of these specs in one project and now bootstrapping the same structure into new repos with `/fd-init`. FDs are tracked through a multi-stage lifecycle (Planned → Design → Open → In Progress → Pending Verification → Complete, plus Deferred/Closed), with commands like `/fd-new`, `/fd-status`, `/fd-explore`, `/fd-deep`, `/fd-verify`, and `/fd-close` managing state transitions.

Technically, the workflow separates roles by tmux window: Planner (spec authoring), Worker (implementation), and PM (backlog grooming). Planning is iterative and text-centric: the author annotates draft plans inline with `%%` markers for unresolved concerns (queue depth, cutover safety, failure cases), then asks the model to reconcile those notes into a revised plan. For hard design questions, `/fd-deep` launches several parallel agents to explore different angles and then merges conclusions. Execution then happens in a fresh worker context, often with “plan mode” and explicit acceptance settings. Verification is partially standardized via `/fd-verify`, which performs a proofread pass, commit, and structured runtime checks.

The article also covers operational ergonomics: tmux window naming/reordering, “go-to” path aliases, and bell/idle hooks that visually mark windows requiring attention. A key empirical boundary is cognitive, not compute: above ~8 concurrent agents, decision quality drops due to context switching overhead.

Why it matters: this is a concrete pattern for teams experimenting with agentic development beyond single-chat coding. It emphasizes durable artifacts over transient chat logs, and explicit lifecycle states over ad-hoc prompting. It also implicitly reframes coding-agent productivity as a workflow design problem: information architecture, checkpoints, and verification loops matter at least as much as model quality.

Caveats: evidence is anecdotal and single-operator; metrics are mostly qualitative; and success appears dependent on strong personal process hygiene. The approach may not transfer cleanly to teams without shared conventions around spec quality, ownership boundaries, and verification rigor.

The commenter questions whether “massively parallel agent” workflows are producing visible, high-quality software outcomes, and frames many such posts as tooling promotion rather than demonstrated engineering impact.

### [Use the Mikado Method to do safe changes in a complex codebase](https://understandlegacycode.com/blog/a-process-to-do-safe-changes-in-a-complex-codebase/)
**Categories:** Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47167058
**Score:** 31 | **Comments:** 14

#### Article Summary
This article presents the Mikado Method as a structured approach to performing risky refactors in large legacy codebases while keeping the system shippable. The author frames the recurring failure mode as “quicksand”: developers begin a high-value change (example: ORM upgrade), hit cascading breakages, stop committing for long periods, and lose predictability.

The proposed process is intentionally mechanical. Start with a concrete goal written down (often on paper), attempt it within a short timebox, and branch based on outcome. If the attempt fails, revert the code entirely, identify prerequisite subgoals, and add them to a dependency graph (Mikado graph). If the attempt succeeds, commit immediately, mark that goal complete, and move to the next unresolved leaf node. Repeat until the root goal becomes straightforward because all prerequisites are already satisfied.

The ORM example demonstrates this dependency decomposition: direct upgrade fails; revert; create subgoals like extracting specific call patterns; complete one quickly; attempt next; when blocked again, revert and split further (“adapt calls in booking/cart” style leaves). The emphasis is less on perfect up-front planning and more on iterative discovery plus disciplined rollback. The author’s “3 advice” section reinforces this: keep timeboxes short (suggested around 10 minutes), commit at each completed subgoal, and use the method for ambitious refactors where maintaining a deployable state is critical.

Why it matters: this is a practical antidote to all-or-nothing refactors. It blends technical decomposition with behavioral safeguards against sunk-cost bias. For teams maintaining brittle systems, the method can improve delivery reliability by converting uncertain “big bang” work into a sequence of verifiable checkpoints.

Limitations are real and mostly implicit: the method does not replace testing strategy; if test coverage is poor, small-step progress can still miss interface-level regressions. It also adds process overhead and demands discipline with frequent revert/commit cycles. In fast-moving delivery contexts, teams may resist that overhead unless they’ve already felt the cost of uncontrolled refactors.

#### Comment Thread Overview
Sentiment is mixed-to-pragmatic. The most upvoted critiques argue the “safe changes” framing can be overstated without adequate tests: reverting and decomposing work helps planning, but safety ultimately depends on validation coverage. Several replies agree that legacy systems often lack reliable tests and suggest the first practical move is building baseline tests and using coverage tools before trusting refactors.

Other commenters defend the method as a useful graph-based planning technique (DAG decomposition) rather than magic. There are first-hand notes from engineers using similar commit-ordered iterative workflows, including adaptations for agent-assisted development, and an observation that strict reset boundaries help avoid “poisoned” session state when models go off-track.

Skeptical comments call the method “common sense with branding,” while supporters counter that naming and explicit procedure are precisely what make practices adoptable across teams. The debate is less about whether decomposition works and more about whether Mikado adds unique value beyond generic timeboxing and incrementalism.

Overall, the thread converges on a balanced view: Mikado is useful as a refactoring control framework, especially for work decomposition and commit hygiene, but it must be paired with credible testing to justify the “safe” claim.

### [GitHub - mandel-macaque/memento: Keep track of your codex sessions per commit](https://github.com/mandel-macaque/memento)
**Categories:** AI Agents, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47212355
**Score:** 403 | **Comments:** 348

#### Article Summary
`git-memento` is a Git extension focused on preserving AI-assisted development provenance by attaching session traces to commits via `git notes`. The core idea is to keep normal Git commit flow intact while storing a cleaned markdown representation of the model session as metadata associated with the commit SHA, rather than embedding long transcripts directly into commit messages or code comments.

The repository documents several command families. `git memento init` configures provider settings per repo (Codex default, Claude supported). `git memento commit <session-id> -m ...` performs a commit and writes the corresponding session note. `git memento amend` preserves prior notes and can append a new session trace, enabling multi-session lineage per commit. Beyond local capture, the tool adds operational commands for governance: `audit` checks note coverage and metadata validity over ranges; `doctor` inspects provider and notes-ref setup; `notes-sync` fetches/merges/pushes notes with backup refs; `notes-rewrite-setup` configures Git rewrite behavior for note carry-through during rebase/amend; `notes-carry` supports squash/rewrite recovery by appending provenance blocks.

Implementation-wise, the project appears to be a .NET CLI with NativeAOT build targets (macOS/Linux/Windows), an install script for release binaries, and a GitHub Action integration in two modes: `comment` (post notes as commit comments) and `gate` (CI enforcement of note coverage/structure). The README also documents provider env vars and command argument defaults for fetching/listing sessions.

Why it matters: teams adopting coding agents increasingly need auditable intent, reproducibility clues, and post-hoc context about why changes happened. `git-memento` offers one concrete design point: preserve conversation artifacts without polluting primary history, and enforce provenance policies through CI. That can improve onboarding, incident analysis, and compliance narratives where “who/what/why” around AI-generated code is important.

Caveats include storage/noise tradeoffs (chat logs can be verbose), integration complexity across rebases/squashes, and uncertain long-term utility of raw transcripts as models/tools evolve. The tool’s design acknowledges this by separating notes from commit body and adding normalization/metadata conventions, but organizational value still depends on disciplined usage and clear review expectations.

#### Comment Thread Overview
Sentiment is strongly engaged and mixed. The largest cluster of comments is practical workflow-sharing: many developers describe keeping `project.md`/`plan.md`/`debug.md` artifacts, iterating plans with the model, and committing distilled planning outputs rather than raw chats. There is meaningful first-hand experience from people using these document-centric workflows on both greenfield and legacy codebases, often with explicit test/debug loops.

The central debate is granularity and audience. One side argues full session logs are too noisy, include dead ends, and are analogous to keeping every micro-step of human coding; they prefer distilled artifacts (plans, final docs) plus diffs. The other side argues provenance is valuable for future humans/agents, especially for recovering architectural intent and assumptions that may not survive into code comments.

Notable side discussions include tools/protocols for agent orchestration, use of MCP versus simpler context mechanisms, and examples of adding AI review loops or CI notes publishing. A recurring concern is “artifact drift”: plan files can become stale by implementation end, so some commenters recommend generating a final authoritative summary document post-merge.

Overall, the thread does not converge on one standard, but consensus emerges around one principle: preserve intent somehow, and optimize the artifact format for future readers rather than raw transcript completeness.

### [Show HN: Omni – Open-source workplace search and chat, built on Postgres](https://github.com/getomnico/omni)
**Categories:** Databases, AI Agents, LLMs, Coding Improvements
**HN Link:** https://news.ycombinator.com/item?id=47215427
**Score:** 101 | **Comments:** 28

#### Article Summary
Omni is an open-source workplace assistant/search platform positioning itself around a “Postgres-first” architecture. The project combines enterprise search and agentic chat: connectors ingest data from workplace systems, content is indexed for both lexical and semantic retrieval, and a chat interface can invoke tools to search/read indexed sources and run sandboxed code for analysis.

The headline technical claim is consolidation: BM25 full-text search (via ParadeDB), vector search (pgvector/HNSW), and application data all live in PostgreSQL. The team explicitly avoids Elasticsearch and separate vector stores, arguing operational simplicity: fewer systems to operate, backup, and tune; transactional consistency between app state and search index; and reduced sync-lag failure modes common in dual-store pipelines.

The README lists core services by stack: Rust for search/index/connector-manager components, Python for AI/LLM orchestration, and SvelteKit for the web frontend. Connector processes run as separate lightweight containers so each can carry source-specific dependencies without polluting global runtime. The AI execution path is constrained with sandbox controls: isolated Docker network, no internal-service/internet access from that environment, Landlock filesystem restrictions, resource limits, and read-only root filesystem.

Feature-wise, Omni emphasizes enterprise concerns: permission inheritance (users only see content they are authorized to access), BYO model provider (Anthropic/OpenAI/Gemini or open-weight via vLLM), and deployment paths for single-host and cloud infra (Docker Compose and Terraform for AWS/GCP). Supported integrations include Google Workspace, Slack, Confluence, Jira, HubSpot, web sources, Fireflies transcripts, and local files.

Why it matters: Omni captures a broader trend in AI product architecture toward minimizing infra sprawl while still supporting hybrid retrieval and tool-using agents. For engineering teams, “one database” can materially reduce operational complexity early on, especially when integrating many connectors quickly.

Caveats/open questions are acknowledged in comments: scale characteristics versus dedicated search/vector systems at higher volumes, connector-specific permission edge cases (especially private channels and changing memberships), and benchmark transparency (the author cites experiments up to roughly 100k–500k rows with p95 under one second, while noting index tuning/benchmark harness work is ongoing).

#### Comment Thread Overview
Sentiment is generally constructive with healthy skepticism. Discussion clusters around three themes: security/privacy realism, Postgres-at-scale tradeoffs, and permission modeling complexity.

On privacy, commenters push back on broad “no data leaves your network” wording, noting that external LLM API calls can still move data unless private endpoints are used. The author agrees and says messaging should be clarified. There is useful nuance around deployment environments: some point out that even cloud VPC hosting may be insufficient for export-controlled workloads, while others note private cloud inference endpoints satisfy many enterprise requirements.

On architecture, experienced users largely validate the Postgres-first approach for early/mid scale, highlighting transactional consistency and avoiding Elasticsearch operational overhead. A notable technical caution raised is potential GIN index bloat/autovacuum pressure with many schemas. Comparisons to alternatives like Onyx/Danswer also appear, reflecting active market benchmarking by practitioners.

The most practical thread concerns permissions. A top question asks how multi-user ACL inheritance is implemented across connectors. The author shares a concrete limitation: Slack connector currently indexes public channels, with private-channel inheritance still being built because membership changes require ongoing permission updates.

Overall, comments treat Omni as promising and technically coherent, while emphasizing that permission correctness and scale benchmarking will determine enterprise credibility.

#### Article Summary
`neocaml` is a new Emacs major mode package for OCaml, built on Tree-sitter and aimed at a lighter, more modern editing experience than older OCaml modes. The author (Bozhidar Batsov) positions it as a practical middle ground: `caml-mode` is considered dated, while `tuareg-mode` is powerful but complex.

The README frames the project’s scope clearly: two major modes (for `.ml` and `.mli`) plus REPL integration (`neocaml-repl`). Feature coverage is broad for an editor mode at this stage: Tree-sitter syntax highlighting with configurable depth, Tree-sitter indentation with cycle-indent behavior, language-aware navigation, imenu support, implementation/interface toggling (`C-c C-a`), comment/edit helpers, compile-regexp integration for OCaml diagnostics, and `_build` artifact awareness. It also includes Eglot integration guidance (with `ocamllsp`) and optional pairing with `ocaml-eglot` for additional LSP operations.

Installation paths include MELPA, `package-vc-install`, and Emacs 30+ `use-package` VC config. The docs emphasize grammar setup (`neocaml-install-grammars`) and advise removing conflicting OCaml major modes to avoid file association clashes. Planned future work currently lists dune integration.

Why it matters: OCaml tooling in Emacs has historically split between mature-but-heavy and lightweight-but-incomplete modes. A maintained Tree-sitter-first mode with modern Emacs/LSP conventions can improve everyday developer experience for OCaml users, especially those already standardized on Eglot and newer Emacs versions. This sits in the broader trend of parser-based editor modes replacing regex-heavy syntax logic and enabling richer structural navigation/indentation behavior.

Caveats: the project is still evolving (planned items remain), Tree-sitter indentation behavior is acknowledged as still needing refinement in edge cases, and adoption depends on ecosystem fit (existing users of tuareg/caml-mode may face migration friction).
